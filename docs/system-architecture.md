# Kiến trúc hệ thống

Monorepo `localman-next` là pnpm workspace gồm `apps/*` và `packages/*`, chạy trên Node ≥ 22 và TypeScript strict (ESM).

## Bố cục

| Thư mục | Package | Vai trò |
|---|---|---|
| `apps/web` | `@localman/web` | Dashboard React 19, Vite 7, Tailwind 4 và React Router 7. Dev server ở cổng 5173 |
| `apps/api` | `@localman/api` | Hai server Express 5 trong một process: dashboard API ở cổng 4000 và mock runtime công khai ở cổng 4100 |
| `packages/operations` | `@localman/operations` | Operation registry: một khai báo sinh route REST, MCP tool descriptor và OpenAPI 3.1. Xem [operation-registry.md](operation-registry.md) |
| `packages/shared` | `@localman/shared` | Code dùng chung cho web và api. `plan-limits.ts` là nguồn duy nhất của mọi hạn mức gói. Ngoài entry gốc có subpath nhẹ: `@localman/shared/constants` (hạn mức, giới hạn resource, `FIELD_TYPES`, `ENDPOINT_*`, `parentKeyOf`; không zod, không catalog Faker), `@localman/shared/faker-catalog` (danh sách id Faker, không Faker) và `@localman/shared/faker-methods` (hàm chạy Faker, chỉ api) |
| `packages/design-tokens` | `@localman/design-tokens` | `tokens.css`, nơi duy nhất được chứa literal màu. Xem [design-system.md](design-system.md) |
| `apps/tunelo-server`, `packages/tunelo-cli`, `packages/tunelo-shared` | `@tunelo/server`, `tunelo`, `@tunelo/shared` | Tunelo, gộp từ repo cũ và giữ nguyên lịch sử. Xem `docs/tunelo/` |
| `scripts/` | — | Script kiểm tra cho CI (`check-mcp-coverage.ts`, `check-tokens.ts`) và script build của Tunelo (`scripts/tunelo/`) |
| `infra/tunelo/` | — | nginx, certbot, PM2 và `deploy.sh` của Tunelo |

Các internal package `@localman/*` là package chỉ có source TypeScript: `exports` trỏ thẳng vào `src/index.ts`. Vite, Vitest và tsx đọc source trực tiếp. Bản build production của api dùng esbuild bundle các package này vào `apps/api/dist/main.mjs` (`apps/api/scripts/build-api.ts`).

## Luồng request của api

```
apps/api/src/main.ts
  ├─ loadEnv()            zod validate biến môi trường, sai thì log fatal và exit 1
  ├─ connectMongo()       không kết nối được thì exit 1 (fail-fast, PM2/Compose tự restart)
  ├─ initModels()         chờ mọi model dựng xong index; index unique dựng lỗi thì exit 1
  ├─ dashboard app :4000  helmet → CSRF guard → với route có `bodyLimit`: kiểm phiên (ẩn danh 401 trước khi đọc body) rồi json theo route → json 100kb → /auth/*, /internal/audit-events → /api/v1/openapi.json → no-store + router từ registry → /healthz → 404 → error handler
  └─ mock app      :4100  helmet (CORP cross-origin) → request id → CORS (preflight 204) → đọc secret → rate limit → json 100kb → mock router → /healthz → 404 → error handler
```

- Phần khung dùng chung cho hai server nằm ở `apps/api/src/http/create-base-app.ts`.
- `/healthz` luôn trả 200 kèm trạng thái kết nối DB, kể cả khi Mongo rớt giữa chừng.
- Mọi lỗi trả về dạng `{ "error": { "code", "message", "details"? } }`. Lỗi không lường trước trả 500 `INTERNAL_ERROR`, không lộ stack.
- SIGTERM/SIGINT đóng cả hai server rồi ngắt Mongo; quá 10 giây thì ép thoát.

## Đăng nhập và phiên

Localman không giữ mật khẩu. User đăng nhập ở IdP dùng chung `auth.hoandat.com` (repo `hoandat-auth`, hợp đồng ở `docs/integration-guide.md` của repo đó); Localman là client OIDC confidential `localman-web` (`apps/api/src/modules/auth/`).

- **Đăng nhập:** `GET /auth/login` tạo `state`, `nonce`, PKCE verifier, dựng URL tới IdP (scope `openid profile email telegram`, không `offline_access`, không `resource`, nên access token là opaque và làm được subject của token exchange), rồi mới lưu transaction ở `login_transactions` (TTL 10 phút). Trình duyệt chỉ giữ một handle ngẫu nhiên trong cookie `lm_login` (SameSite=Lax). Giới hạn 20 lần mỗi phút cho mỗi IP; vượt thì 303 về `/?authError=rate_limited`. IdP không phản hồi thì 303 về `/?authError=idp_unavailable`. Cả hai là điều hướng trình duyệt nên không trả JSON.
- **`returnTo` và link nội bộ:** chỉ nhận path bắt đầu bằng một `/`. Path được chuẩn hoá như trình duyệt (dot segment, `%2e`) rồi kiểm lại, nên `/.//evil.com` hay `/%2E%2E//evil.com` (chuẩn hoá thành `//evil.com`) bị chặn và về `/projects`. Luật này nằm ở `http/internal-path.ts`, dùng chung cho `link` của thông báo.
- **Callback:** transaction chỉ bị tiêu khi `state` của callback khớp, nên một callback giả không huỷ được lượt đăng nhập thật đang chờ. Sau đó đổi code (kiểm state, nonce, PKCE), đọc `userinfo` để upsert user (`users`, kèm chat Telegram), tạo phiên mới và đặt cookie `__Host-lm_session` (HttpOnly, Secure, SameSite=Strict, Path=/; trên http dev là `lm_session`). Lỗi thì về `/?authError=access_denied|login_expired|login_failed|idp_unavailable|rate_limited`.
- **Phiên** (collection `sessions`): `_id` là SHA-256 của giá trị cookie; `sub`, `sid` của IdP, access/refresh/ID token mã hoá chung một blob AES-256-GCM (AAD là id phiên, key từ `SESSION_ENCRYPTION_KEY` có key id để xoay vòng). Hết hạn 30 ngày không dùng, tối đa 90 ngày, giống grant của IdP. Huỷ phiên (đăng xuất, back-channel, refresh bị từ chối) thì xoá luôn các thiết bị Web Push mà phiên đó đã đăng ký.
- **Refresh:** access token còn dưới 60 giây thì refresh ngay khi xử lý request. Refresh token xoay vòng và dùng lại sẽ làm IdP thu hồi grant, nên mỗi phiên chỉ một lượt refresh: request cùng process dùng chung một promise, các process khác nhường nhau qua lease `refreshLockedUntil` trên document phiên. Refresh xong đọc lại `userinfo`. IdP trả `invalid_grant` thì xoá phiên (401).
- **Khi IdP sập (đánh đổi có chủ ý):** lỗi refresh tạm thời không xoá phiên; request vẫn chạy bằng access token cũ tới khi nó hết hạn (15 phút). Sau đó mọi API có scope trả 503 `AUTH_UNAVAILABLE` cho tới khi IdP trở lại, thay vì cho dùng tiếp một phiên mà IdP không còn xác nhận được.
- **Đăng xuất:** `POST /auth/logout` (form) xoá phiên rồi 303 tới `end_session_endpoint` với `id_token_hint`. `POST /auth/backchannel-logout` nhận logout token từ IdP, xác minh bằng JWKS (`iss`, `aud=localman-web`, `typ=logout+jwt`, `iat` trong 2 phút, sự kiện back-channel, không `nonce`, có `sid` hoặc `sub`), huỷ phiên theo `sid` (hoặc mọi phiên của `sub`) rồi mới ghi `jti` vào `logout_token_jtis`, để lượt IdP gửi lại vẫn đăng xuất được nếu bước ghi lỗi.
- **Sự kiện audit:** `POST /internal/audit-events` nhận SET (`application/secevent+jwt`, ES256, `typ: secevent+jwt`, `aud` là URL đầy đủ của endpoint `${PUBLIC_URL}/internal/audit-events`, `iat` không quá 15 phút và `exp` không quá 15 phút sau `iat`, dung sai đồng hồ 30 giây) kèm `Authorization: Basic` so khớp constant-time với `AUDIT_CLIENT_ID`/`AUDIT_CLIENT_SECRET`; thiếu hai biến này thì route trả 404. `jti` (bằng `Idempotency-Key`) lưu ở `audit_events` (30 ngày); sự kiện gửi lại được trả 202 mà không xử lý lại. `method.unlinked` với `method: "telegram"` xoá chat đã lưu ngay; `method.linked` telegram tạm dừng Telegram (`telegram.refreshPendingAt`) cho tới lần đọc `userinfo` kế tiếp (refresh hoặc đăng nhập). `email.reclaimed` xoá email của tài khoản và gỡ các lời mời gắn qua email đó (xem mục Cộng tác viên). Sự kiện khác chỉ được ghi lại.
- **Token exchange:** `TunnelTokenExchange` đổi phiên lấy token `aud=https://tunnel.hoandat.com`, `scope=tunnels:read` (RFC 8693), cache theo phiên tới gần hết hạn. Phase 10 dùng.
- Mọi response `/api/v1/*` có `Cache-Control: no-store`; các route `/auth/*` và `/internal/*` cũng vậy.

## Proxy và IP của client

Localman deploy theo quy ước của server .65: pm2 chạy API, nginx giữ TLS và chạy **cùng máy**. Vì vậy `TRUST_PROXY` mặc định `loopback` (tương đương `127.0.0.1` và `::1`) là đúng: chỉ nginx trên máy được đặt `X-Forwarded-For`, và giới hạn theo IP (`GET /auth/login`) thấy IP thật của client. Giá trị được kiểm lúc khởi động bằng chính `proxy-addr` mà Express dùng: IP/CIDR sai làm API không khởi động. `true` luôn bị từ chối (ai cũng giả được `X-Forwarded-For`); ở production số hop cũng bị từ chối, phải ghi địa chỉ. Nếu chạy sau proxy khác (load balancer, Cloudflare Tunnel, nginx ở máy khác) thì phải đặt `TRUST_PROXY` bằng đúng địa chỉ hoặc CIDR của proxy đó, nếu không mọi request bị tính chung một IP.

## Thông báo

Không có email. `apps/api/src/modules/notifications/` gửi mỗi sự kiện tới các kênh user chọn cho loại sự kiện đó (`notification_preferences`):

- **Trong app** (mặc định bật, tắt được theo từng loại): lưu ở `notifications` (giữ 90 ngày), là dữ liệu của chuông.
- **Web Push** (mặc định tắt): VAPID (`VAPID_*`, tuỳ chọn), subscription theo thiết bị (`push_subscriptions`, endpoint duy nhất, chỉ nhận host của dịch vụ push trình duyệt), gắn với phiên đã đăng ký nó. Phiên kết thúc hoặc hết hạn thì thiết bị không nhận push nữa và bị xoá. Dịch vụ push trả 404/410 thì xoá subscription.
- **Telegram** (mặc định tắt): bot riêng của Localman (`TELEGRAM_BOT_TOKEN`, tuỳ chọn), `chatId` lấy từ `userinfo` của IdP. 429 thì gửi lại theo `retry_after` hoặc backoff luỹ thừa, tối đa 3 lượt và chờ không quá 10 giây; 403 thì đánh dấu kênh chưa kích hoạt cho tới khi chat đổi hoặc user bật lại Telegram trong tuỳ chọn.

`notify()` lưu bản trong app rồi trả về ngay; Web Push và Telegram chạy nền, lỗi chỉ ghi log. Khi tắt server, `drain()` chờ các lượt gửi nền xong. Danh mục sự kiện ở `notification-events.ts`; module khác gọi `getNotificationService().notify(sub, { type, title, body, link })`.

## Projects và giới hạn gói

Module `apps/api/src/modules/projects/`, operation `mock.*` dưới `/api/v1/projects`: `listProjects` (`GET /projects`), `getProject` (`GET /projects/:projectId`, cùng shape với một item của danh sách, 404 khi không đọc được, không tồn tại hoặc đang xoá), `createProject`, `updateProject`, `deleteProject`, `cloneProject`, `rotateProjectSecret` (`POST /projects/:projectId/rotate-secret`).

- **Project** (collection `projects`): `name`, `prefix`, `secret`, `owner` (`sub`), `quotaSlot`, timestamps. Zod của tên và prefix nằm ở `packages/shared/src/project-schema.ts`, web và api dùng chung. Tên bắt đầu bằng chữ hoặc số, sau đó nhận chữ mọi ngôn ngữ (có tiếng Việt, chuẩn hoá NFC), số, `_`, khoảng trắng, `-` và dấu ngoặc (để bản clone "X (copy)" sửa được mà không phải đổi tên). Prefix theo `^[\w\-/]*$` rồi chuẩn hoá thành `/x/y`, rỗng là không có prefix. Prefix trùng nhau trong cùng owner được phép như mockapi.io, vì mỗi project có subdomain riêng theo secret.
- **Secret** là nhãn DNS của mock runtime (owner xoay được, xem Phân quyền): nanoid 24 ký tự chỉ gồm `a-z0-9` (hostname không phân biệt hoa thường, `_` không hợp lệ trong hostname), khoảng 124 bit, unique index. `mockBaseUrl` = `https://{secret}.{MOCK_BASE_DOMAIN}{prefix}`; domain `localhost…` dùng `http`.
- **Phân quyền:** `project-access.ts` chỉ để lộ `can(user, action, project)` (`read`, `editResources`, `clone`, `update`, `delete`, `manageMembers`) và `accessibleProjectsFilter(user)` cho truy vấn danh sách. Owner làm được mọi việc; collaborator đã accept được `read`, `editResources` (resource và dữ liệu) và `clone`, không sửa/xoá project và không quản lý thành viên. Quyền dashboard đọc từ Mongo mỗi request (không cache), nên rời hoặc bị xoá là mất quyền dashboard ngay. URL mock (secret) là quyền kiểu bearer: ai biết URL đều gọi được mock API, kể cả thành viên đã bị xoá. Muốn chặn hẳn, owner xoay secret bằng `rotateProjectSecret` (chỉ owner, `dryRun` trả số collaborator sẽ được báo): secret mới sinh như lúc tạo project, mục cache của secret cũ bị xoá ngay nên URL cũ trả 404 tức thì, dữ liệu giữ nguyên, các collaborator còn lại nhận thông báo `project.mockUrlChanged`. Không đọc được project thì 404 `NOT_FOUND` để không lộ project tồn tại; đọc được nhưng không có quyền thao tác thì 403 `FORBIDDEN`. View project (danh sách và `getProject`) có `role` và `memberCount` (owner cộng collaborator đã accept).
- **Dữ liệu phụ thuộc:** module khác đăng ký `registerProjectDependent({ kind, count, deleteAll, copy? })` ở `project-dependents.ts`. Xoá project (`dryRun` trả số lượng theo `kind`) đi ba bước, lặp lại an toàn: (1) dưới khoá project (`projects/project-lock.ts`, `inProjectTransaction`) đặt tombstone `deletingAt`; từ đó project coi như đã mất với mọi lượt đọc và ghi (404, không hiện trong danh sách), trừ `DELETE`; (2) gọi `deleteAll` (idempotent) của từng dependent; (3) xoá document project, lúc này slot hạn mức project mới được trả. Bước 2 lỗi thì tombstone ở lại, project vẫn chiếm slot, và `DELETE` lần sau dọn tiếp. Lượt ghi resource chạy đua với bước 1 hoặc commit trước (rồi bị bước 2 dọn), hoặc xung đột trên khoá, chạy lại và nhận 404, nên không còn dữ liệu mồ côi. Tombstone cũng là nền cho thùng rác 30 ngày (`trashDays`) sau này. Clone tạo project mới (secret mới, tên "X (copy)" cắt theo code point cho vừa giới hạn, tính vào hạn mức của người clone) rồi gọi `copy` của từng dependent; `copy` lỗi thì xoá bản clone dở. Dependent không có `copy` (thành viên) không đi theo bản clone.
- **Hạn mức project** (`billing/plan-guard.ts`): chỉ đếm project user sở hữu, theo `limitsFor(plan).projects`; vượt thì 403 `PLAN_LIMIT_REACHED` kèm `details: { limit: "projects", max, used }`. Pro có `planExpiresAt` đã qua thì tính như Free (cả ở `GET /users/me`). Chống tạo song song vượt hạn mức không cần transaction: mỗi project giữ một `quotaSlot`, unique index `(owner, quotaSlot)`. Lượt tạo đọc các slot đang dùng, từ chối khi đủ hạn mức, rồi lấy slot trống nhỏ nhất; các lượt đọc cùng dữ liệu chọn cùng một slot nên chỉ một lượt insert thắng, các lượt khác đọc lại và kiểm lại.
- **Bộ đếm tháng** (`billing/usage-counter-model.ts`, collection `usage_counters`): một document theo `ownerSub` + `yyyymm` (tháng theo lịch Asia/Saigon) với `mockRequests` và `proxyRequests`; `incrementUsage()` tăng nguyên tử và trả tổng mới cho mock runtime và proxy. `GET /api/v1/account/usage` trả gói đang áp dụng, project đã dùng và hai bộ đếm tháng so với hạn mức; `max: null` là không giới hạn (`Infinity` được map tường minh).
- **Gán gói tạm thời** (chưa có billing): `MONGO_URI=… pnpm --filter @localman/api set-user-plan --username <u> --plan pro --expires YYYY-MM-DD` (`--expires` tính hết ngày đó theo giờ Saigon, ngày đã qua phải thêm `--force`; `--plan free` xoá hạn). Script chỉ in `sub`, `username`, `plan`, `planExpiresAt`.

## Cộng tác viên và magic link

Module `apps/api/src/modules/collaborators/`, operation `mock.*`: `listCollaborators`, `lookupInvitee`, `inviteCollaborator`, `removeCollaborator` dưới `/api/v1/projects/:projectId/collaborators`; `getMagicLink`, `rotateMagicLink`, `revokeMagicLink` ở `/api/v1/projects/:projectId/magic-link`; `previewInvite`, `acceptInvite` ở `/api/v1/invites/{preview,accept}` (token nằm trong body, không bao giờ trong URL của API; miễn MCP vì chỉ người được mời mở trên trình duyệt).

- **Trần thành viên:** `limitsFor(gói hiệu lực của owner).membersPerWorkspace` (Free 3, Pro 10), tính owner, collaborator đã accept và lời mời còn hạn. Lời mời hết hạn không giữ chỗ, vẫn hiện cho owner với `status: "expired"` (xoá tự động 30 ngày sau hạn); magic link không giữ chỗ, trần kiểm lúc tham gia. Vượt thì 403 `PLAN_LIMIT_REACHED` với `details: { limit: "members", max, used }` (web mở modal gói với nguồn `plan_limit_members`). Hạ gói giữ nguyên quyền của mọi thành viên hiện có; chỉ lời mời mới, accept lời mời đang chờ và tham gia qua magic link bị chặn cho tới khi số chỗ xuống dưới trần. Mọi lượt ghi (mời, accept, tham gia, tạo magic link) chạy trong `inProjectTransaction`: hai lượt cùng project ghi chung document khoá nên một lượt chạy lại trên kết quả của lượt kia, không thể cùng lọt trần; project đã có tombstone thì 404.
- **Mời** (chỉ owner): username (`@` tuỳ chọn) hoặc email, khớp chính xác không phân biệt hoa thường, không tìm theo tiền tố. Email gắn vào tài khoản có email đó đã được IdP xác minh; nếu không có, chỉ gắn khi đúng một tài khoản chưa xác minh dùng email đó (nhiều hơn một thì lời mời chỉ gắn email). Khớp tài khoản thì gắn `inviteeUserId` và gửi thông báo `project.invitation` (trong app, Web Push, Telegram theo tuỳ chọn) kèm link; email chưa có tài khoản thì gắn `inviteeEmail` (lowercase), owner tự gửi link. Không có lời mời không gắn ai. Thẻ tài khoản khớp chỉ có username, tên, avatar, email đã che và `emailVerified` để owner nhận ra tài khoản giả. Mời bản thân trả 400 `CANNOT_INVITE_SELF`, mời thành viên 409 `ALREADY_MEMBER`, username không tồn tại 404 `INVITEE_NOT_FOUND`, đều không kèm thông tin tài khoản. `lookupInvitee` và `inviteCollaborator` dùng chung ngân sách 20 lượt mỗi giờ mỗi owner (`inviteRateLimit`, 429 `RATE_LIMITED`) để không thành công cụ dò tài khoản. Mời lại cùng người hoặc cùng email thì cấp token và hạn mới trên dòng cũ nhất (danh tính dựng lại theo lần mời mới), link cũ hết hiệu lực. Thành viên từng được mời ở một email mà nay không còn dùng email đó không bị coi là người được mời lại.
- **Token:** 32 byte ngẫu nhiên (base64url), chỉ lưu SHA-256, trả về đúng một lần (`inviteLink` hay `link`, dạng `/invite/:token` cho cả hai loại), TTL 7 ngày. Lời mời dùng một lần; magic link dùng lại được, mỗi project tối đa một link (tạo mới thay hash, link cũ ngừng ngay; thu hồi đặt `revokedAt`). `getMagicLink` chỉ trả trạng thái `none | active | expired | revoked`, hạn và thời điểm tạo.
- **Accept:** preview và accept đều cần đăng nhập và bị giới hạn 30 lượt mỗi 10 phút mỗi tài khoản, 60 mỗi IP (`inviteTokenRateLimit`). Lỗi token tách mã: 404 `INVITE_NOT_FOUND` (không có, đã bị thay, project đã xoá), 410 `INVITE_EXPIRED` (`details.expiresAt`), 410 `INVITE_USED`, 410 `INVITE_REVOKED`. Project lấy từ token đã lưu, không từ request, nên token chỉ dẫn vào đúng project của nó. Điều kiện của lời mời: gắn tài khoản thì chỉ tài khoản đó (403 `NOT_INVITEE`); gắn email thì chỉ tài khoản có email được IdP xác minh qua Google/GitHub trùng email đó sau khi lowercase (email chưa xác minh chỉ trùng chữ: 403 `EMAIL_NOT_VERIFIED`). Magic link nhận mọi người đã đăng nhập. Owner và thành viên nhận `alreadyMember: true` mà không đổi gì. Accept hay tham gia thì các dòng chờ khác của người đó (gắn tài khoản, hoặc chưa gắn mà trùng email đã xác minh của họ) được gộp vào, trả lại chỗ. Preview trả `kind`, project, người mời, hạn, email mời đã che, `eligible` và `reason` (`NOT_INVITEE`, `EMAIL_NOT_VERIFIED`, `ALREADY_MEMBER`, `MEMBER_LIMIT`).
- **Danh sách và rời:** owner thấy mọi dòng kèm email mời; collaborator chỉ thấy owner và thành viên đã accept, không có email. Owner xoá được mọi dòng; collaborator chỉ xoá dòng của mình (rời project).
- **Email bị chiếm lại:** sự kiện audit `email.reclaimed` (tài khoản khác ở IdP đã xác minh email này) xoá email khỏi bản sao user, đặt `emailVerified: false`, và gỡ `inviteeUserId` khỏi các lời mời đang chờ đã gắn tài khoản đó qua email; lời mời vẫn gắn email nên chủ email đã xác minh accept được.
- **Index:** token, `(projectId, inviteeUserId)` và `(projectId, inviteeEmail)` là unique partial theo `$exists` (planner dùng được cho truy vấn bằng), thêm `(projectId, status)` cho đếm chỗ và `memberCount`; `users.username` và `users.email` có index collation `en` strength 2 (`CASE_INSENSITIVE_COLLATION`).
- **Project dependents:** `collaborators` và `magicLinks` (đếm và xoá, không `copy`): xoá project xoá cả thành viên, lời mời và magic link; bản clone không có thành viên.

## Resources và dữ liệu mock

Module `apps/api/src/modules/resources/`, operation `mock.*` dưới `/api/v1/projects/:projectId/resources` (cộng `GET /api/v1/faker-methods`). Zod, whitelist Faker và template nằm ở `packages/shared`, web và api dùng chung. Hằng của resource (`resource-constants.ts`) tách khỏi các module zod (`resource-schema.ts`, `resource-templates.ts` re-export lại), để web đọc qua `@localman/shared/constants` mà không kéo zod và catalog Faker vào trang; catalog chỉ nằm trong chunk modal resource.

- **Resource** (collection `resources`): `projectId`, `parentId` (cây cha–con), `name` (một đoạn path: `^[A-Za-z0-9][\w-]*$`, tối đa 64), `schema[]`, `template` (object template hoặc `null`), `endpoints[]` (đúng 5 endpoint `GET /:res`, `GET /:res/:id`, `POST /:res`, `PUT /:res/:id` dùng chung cho PATCH, `DELETE /:res/:id`, mỗi cái `enabled` và `response`), `count`, `nextId`, `ownerSub`, `quotaSlot`. Unique `(projectId, parentId, name)`: tên chỉ cần khác giữa các anh em. Cây sâu tối đa `MAX_RESOURCE_DEPTH` (10) tầng.
- **Schema:** field `{ name: /^[\w\-.]+$/, type, fakerMethod?, childId? }`, tối đa 50 field, không được tên `__proto__`, `constructor`, `prototype` (cùng danh sách `FORBIDDEN_KEYS` với key JSON). `id` (Object ID) và `{parent}Id` (Parent ID, `parentKeyOf(tên cha)`: `users` → `userId`) là field hệ thống, không nằm trong `schema`; field schema hay key cấp một của object template trùng tên với chúng bị từ chối (giá trị sẽ bị giá trị sinh ra che mất). Đổi tên cha mà bản ghi con đã có key trùng `{parent}Id` mới thì 409 `FIELD_CONFLICT`. `Parent Resource` và `Child Resource` là field quan hệ: không lưu vào record, mock runtime phân giải khi trả lời. Mặc định khi tạo: `createdAt` (`date.past`), `name` (`name.fullName`), `avatar` (`image.avatar`).
- **Record** (collection `records`): `resourceId`, `projectId`, `id` (chuỗi), `parentRecordId`, `data`. `id` và `parentRecordId` là cột riêng, không nằm trong `data`, nên đổi tên hay đổi cha không phải viết lại record; `toRecordView` ghép thành `{ id, {parent}Id, ...data }`. Unique `(resourceId, id)`, index `(resourceId, parentRecordId)`; thứ tự là thứ tự chèn (`_id`).
- **Whitelist Faker** (`faker-method-catalog.ts` cho danh sách id, `faker-methods.ts` cho hàm chạy, import qua `@localman/shared/faker-methods` để web không kéo Faker vào bundle): 249 method theo 21 nhóm, id giữ tên của nguồn (Faker 5: `name.*`, `address.*`, `datatype.*`) và map sang API Faker 10. Mỗi id là một hàm gọi tĩnh; tra cứu bằng `Map`, nên `constructor`, `__proto__` hay `helpers.fake` không gọi được gì. Kết quả luôn là JSON (ngày thành chuỗi ISO). Faker 10 bỏ LoremFlickr, nên các id ảnh theo chủ đề của nguồn (`image.cats`, `image.urlLoremFlickr`…) trả URL ảnh chung.
- **JSON template** (`json-template.ts`): chỉ thay khi **cả chuỗi** là một biến: `"$mockData"`, `"$count"` (chỉ trong custom response) hoặc `"$category.method"`. Chuỗi dài hơn như `"Giá $5"` giữ nguyên. Lúc lưu, tham chiếu lạ bị 400 (bắt lỗi gõ như `$mockdata` và `$constructor.constructor`); lúc render, tham chiếu lạ giữ nguyên chữ, không bao giờ chạy. Object được dựng lại bằng `Object.fromEntries` nên key `__proto__` không chạm prototype; key `__proto__`, `constructor`, `prototype` bị từ chối ở đầu vào (mongoose âm thầm bỏ `__proto__`). Giới hạn lúc lưu: template sâu 10, 2.000 giá trị, tối đa `MAX_METHOD_REFERENCES` (200) lời gọi Faker. Lúc render (`json-template-render.ts`) đầu ra được đo **trong khi** sinh, theo số giá trị (50.000) và theo byte (`maxBytes`, ước lượng JSON gọn); vượt là dừng ngay với `TEMPLATE_TOO_LARGE`, nên template quá lớn chỉ tốn tối đa một ngân sách công sức.
- **Sinh dữ liệu:** `POST …/:resourceId/generate { count: 0..100 }` thay toàn bộ dữ liệu (0 là reset), id lại từ "1". Field Faker gọi whitelist, `String` ra `"<tên> <số thứ tự>"`, `Number` ra số thứ tự, `Boolean` ngẫu nhiên, `Object` `{}`, `Array` `[]`, `Date` một ngày trong quá khứ (giống nguồn). Có `template` thì dùng template thay schema. Resource con chia ngẫu nhiên N bản ghi cho các bản ghi cha; cha chưa có dữ liệu thì 409 `PARENT_HAS_NO_DATA` (message tiếng Anh, client dịch theo mã). `generate_all` vẫn nguyên tử (một transaction) nhưng sinh và chèn **từng resource** theo thứ tự cha trước con, nên bộ nhớ chỉ giữ dữ liệu của một resource (`count` tuỳ chọn; không có thì giữ số hiện tại, resource rỗng nhận 10 như prototype). `reset_all` xoá mọi bản ghi, giữ schema.
- **Sửa dữ liệu thô:** `PUT …/:resourceId/data { data: [...] }` (registry chỉ nhận body là object, nên mảng nằm trong `data`; riêng route này nhận body tới 2,5 MB, các route khác giữ 100 KB), tối đa `MAX_RECORDS_PER_RESOURCE` (1000, cũng là trần POST của mock runtime; generator dừng ở `MAX_GENERATE_COUNT` = 100) object. `id` tuỳ chọn, duy nhất, là số nguyên không âm hoặc chuỗi an toàn cho URL có ít nhất một chữ hoặc số (chặn `.`, `..`); thiếu thì đánh số tiếp sau id số lớn nhất không quá 10^9. Với resource con, `{parent}Id` phải trỏ tới bản ghi cha có thật (`null` bị từ chối), thiếu thì gán ngẫu nhiên. Lỗi JSON trả đúng `path` của giá trị hỏng.
- **Trần kích thước** (`MAX_RECORD_BYTES` 32 KB mỗi record, `MAX_RESOURCE_BYTES` 2 MB mỗi resource, trong `plan-limits.ts`, áp cho mọi gói): kiểm khi sinh (template dừng sớm theo byte, tổng đo dần), khi `PUT data`, trong `writeRecords` và khi clone; mỗi resource lưu tổng hiện tại ở `dataBytes` (đặt lại ở mọi đường ghi: sinh, `PUT data`, `generate_all`, `reset_all`, clone, reset cây con; resource cũ chưa có trường này được đo lại một lần ở lượt ghi mock kế tiếp); vượt thì 413 `DATA_TOO_LARGE` với `details: { limit: "record" | "resource", maxBytes, actualBytes, resourceId, name }` (`actualBytes` là ước lượng; `generate_all` cũng nêu resource gây lỗi). Lúc lưu, object template được ước lượng record xấu nhất từ bảng trần kích thước từng method Faker (`faker-method-sizes.ts`, đo hàng nghìn lần rồi nhân đôi; test đo lại để bắt khi nâng Faker) cộng phần chữ cố định; vượt 32 KB thì 400 `TEMPLATE_TOO_LARGE` (`details: { maxBytes, estimatedBytes }`).
- **Nhất quán cha–con** (chi tiết ở [ADR-0001](decisions/0001-resource-data-in-project-transactions.md)): mọi thao tác ghi resource hoặc record của dashboard chạy trong transaction Mongo, giữ khoá cây của project rồi kiểm project còn tồn tại và không có `deletingAt` (không thì 404). Sau khi dữ liệu cha bị thay, bản ghi con trỏ tới id cha còn tồn tại được giữ, bản ghi con mồ côi được gán ngẫu nhiên một bản ghi cha mới; cha rỗng thì cả cây con bị reset. Đổi cha (`PUT …/:resourceId/parent`) reset dữ liệu của resource đó và mọi resource dưới nó, bỏ field quan hệ không còn hợp lệ. Xoá resource xoá cả cây con và record, và bỏ field `Child Resource` trỏ tới nó.
- **Hạn mức resource:** `limitsFor(plan).resources` tính trên **mọi resource của mọi project user sở hữu** (tên field không có hậu tố `Per…` như `membersPerWorkspace`), không tính project được chia sẻ. Resource bị tính cho chủ project (`ownerSub`). Chống race giống project: unique `(ownerSub, quotaSlot)`, slot trống nhỏ nhất (`billing/quota-slots.ts`). Clone project tính toàn bộ resource của bản sao vào hạn mức người clone; vượt thì 403 `PLAN_LIMIT_REACHED` (`limit: "resources"`) và bản clone bị xoá. Custom response và object template mở cho mọi gói.
- **Phân quyền:** đọc cần `can(read)`, ghi cần `can(editResources)` của project (owner và collaborator đã accept); không đọc được project thì 404, resource không thuộc project cũng 404. Thao tác xoá hoặc thay dữ liệu (`delete`, `parent`, `generate`, `generate_all`, `reset_all`, `PUT data`) là destructive và nhận `?dryRun=true` để xem trước danh sách `changes` (`countBefore` → `countAfter`).
- **Project dependents:** `resources` (đếm resource; xoá resource, record và khoá cây; clone chép cả cây, schema, template, endpoint và record trong một transaction giữ cả khoá project nguồn, nên đọc một snapshot nhất quán và chép record từng resource; map id resource cũ sang mới, giữ `id` và `parentRecordId` của record) và `records` (chỉ đếm và xoá).
- **Ghi chú cho mock runtime:** key bắt đầu bằng `$` hoặc chứa `.` hợp lệ trong dữ liệu và luôn nằm dưới `data`; không bao giờ dựng đường dẫn filter hay update Mongo từ key dữ liệu (lọc, sắp xếp, merge làm trong bộ nhớ hoặc thay cả `data`). Tên resource anh em phân biệt hoa thường (`Side` và `side` cùng tồn tại được), nên router mock phải so khớp tên phân biệt hoa thường. Cách runtime giữ các điều này: xem mục Mock runtime.

## Mock runtime

Module `apps/api/src/modules/mock-runtime/`, gắn vào app cổng 4100 (`mock-server.ts`). Đây là API công khai do người dùng định nghĩa nên không đi qua operation registry và không có MCP tool (MCP cho dữ liệu mock là các operation `mock.*` của dashboard).

- **Địa chỉ:** secret lấy từ Host `{secret}.{MOCK_BASE_DOMAIN}` (không phân biệt hoa thường như DNS, bỏ cổng, phải là một nhãn DNS hợp lệ), không có thì từ path `/m/{secret}/…` (dùng khi chưa có wildcard TLS hoặc ở local). Sau đó bỏ `prefix` của project (so khớp phân biệt hoa thường). Request không trỏ tới project nào (`/healthz` trên host trần) đi tiếp xuống `/healthz` và 404 chung; trên host của project, `/healthz` là một route mock bình thường.
- **Cache project:** `secret → { id, prefix, owner, plan đã lưu của owner }` trong LRU 10.000 mục, TTL 60 giây, cả secret không tồn tại (lượt dò secret ngẫu nhiên tốn một truy vấn rồi trúng cache có giới hạn). Dashboard chạy cùng process nên đổi prefix hoặc bắt đầu xoá project (tombstone `deletingAt`) xoá mục cache ngay. Thay đổi khác (plan đổi bằng CLI `set-user-plan`) có hiệu lực trễ tối đa 60 giây; ngày hết hạn Pro vẫn được so mỗi request. Cây resource (schema, endpoint) đọc lại mỗi request (một truy vấn theo `projectId`), nên sửa ở dashboard có hiệu lực ngay.
- **Route:** tự tách path thành `[res, id?, childRes, id?, …]` theo cây, độ sâu tuỳ ý, tên so khớp phân biệt hoa thường (không dùng route Express theo tên). Đoạn đầu khớp resource gốc cùng tên, nếu không có thì khớp resource lồng duy nhất mang tên đó (route phẳng `/:child` của nguồn); tên trùng ở nhiều nhánh mà không có gốc thì 404. Route lồng kiểm từng bản ghi tổ tiên tồn tại và đúng cha (`/users/2/posts/1` là 404 nếu post 1 thuộc user khác) và lọc theo `parentRecordId`; route phẳng trả mọi bản ghi.
- **Endpoint:** GET list, GET one (và HEAD), POST, PUT/PATCH (dùng chung endpoint PUT), DELETE. Endpoint tắt, method khác hoặc kết hợp sai (POST lên `/:res/:id`) trả 404. Không tìm thấy project, resource hay bản ghi đều trả 404 với body là chuỗi JSON `"Not found"` như nguồn; các lỗi khác theo dạng `{ error: { code, message } }`.
- **Query (trong bộ nhớ):** tải bản ghi của collection bằng truy vấn cố định trên cột hệ thống (`resourceId`, `parentRecordId`) rồi lọc, sắp xếp, phân trang trong JS trên view của bản ghi. `search`/`filter`: chuỗi con không phân biệt hoa thường trên mọi giá trị chuỗi cấp một (kể cả `id`). `<field>=v` chỉ với field của schema (hoặc key cấp một của object template) và `id`, `{parent}Id`, kết hợp AND; giá trị được ép theo kiểu của giá trị trong bản ghi: chuỗi khớp chuỗi con không phân biệt hoa thường, số và boolean khớp đúng (`completed=false`), `null` khớp chữ `null`, object và mảng không khớp; `id` và `{parent}Id` khớp nguyên chuỗi. Key không phải field bị bỏ qua. `page`/`p`, `limit`/`l` (số nguyên dương; không có `limit` thì trả hết, lớn hơn 100 thì hạ về 100, giá trị hỏng bị bỏ qua). `sortBy`/`sortby`/`orderBy`/`orderby` với field có thật (số và chuỗi số so theo số, nên id "2" trước "10"), `order=desc` (không phân biệt hoa thường), mặc định asc, sort ổn định; field lạ bị bỏ qua. Key bắt đầu bằng `$`, chứa `.`, `[` hoặc `]` (parser "simple" của Express giữ nguyên `title[$ne]` thành tên key), là `__proto__`/`constructor`/`prototype`, giá trị lặp (`a=1&a=2`) và `sortBy` mang tên như vậy đều trả 400 `INVALID_QUERY` trước khi chạm DB. Mọi lượt đọc field dùng `Object.hasOwn`. Field có tên chứa `.` vì thế không lọc được qua query.
- **Ghi:** body là object JSON (thiếu body là `{}`), qua `checkJson` (giới hạn JSON chung, key `FORBIDDEN_KEYS` ở mọi tầng bị 400 `VALIDATION_ERROR`) và được dựng lại từ thuộc tính riêng, nên `{"__proto__":…}` hay `constructor.prototype` không chạm prototype. `id`, `{parent}Id` và tên field quan hệ bị bỏ khỏi dữ liệu. Mọi lượt ghi chạy trong `inProjectTransaction` (khoá project, project bị tombstone thì 404) và ghi bằng driver gốc với cả `data`, nên key `$x`, `a.b` được lưu đúng như dữ liệu, không bao giờ thành toán tử hay đường dẫn.
  - POST: `id = nextId` (bỏ qua id đã có từ dữ liệu dán tay), rồi `nextId + 1`, `count + 1`; field schema (hoặc key template) mà body thiếu được sinh như generator (`FILL_MISSING_FIELDS_ON_CREATE` ở `crud-handlers.ts`), trả 201. Route lồng gán `{parent}Id` theo path (giá trị trong body bị bỏ qua); route phẳng của resource con cần `{parent}Id` trỏ tới bản ghi cha có thật, thiếu hoặc sai là 400.
  - PUT/PATCH: merge body vào dữ liệu (key cũ giữ thứ tự), không đổi `id` hay `{parent}Id`, trả 200.
  - DELETE: trả bản ghi đã xoá (quan hệ phân giải trước khi xoá), xoá dây chuyền bản ghi con theo từng tầng và giảm `count` tương ứng.
  - Trần: `MAX_RECORDS_PER_RESOURCE` (1000) → 409 `RECORD_LIMIT_REACHED`; `MAX_RECORD_BYTES`/`MAX_RESOURCE_BYTES` đo như dashboard → 413 `DATA_TOO_LARGE`; body quá 100 KB → 413 `PAYLOAD_TOO_LARGE`. Trần resource được kiểm **theo delta** trên `dataBytes` của resource (tổng cũ − bản ghi cũ + bản ghi mới), không đọc các bản ghi khác; POST/PUT/PATCH/DELETE và xoá dây chuyền cập nhật `dataBytes` trong cùng transaction.
- **Field quan hệ:** `Parent Resource` nhúng bản ghi cha (một tầng, không phân giải tiếp quan hệ của nó, `null` nếu thiếu); `Child Resource` là mảng bản ghi của resource con trực tiếp thuộc bản ghi này. Phân giải sau khi lọc và phân trang, một truy vấn mỗi field cho cả trang.
- **Response:** template `$mockData` mặc định trả thẳng dữ liệu; template khác render qua `json-template` với `$mockData`, `$count` và `$category.method` (Faker chạy mỗi request, tham chiếu lạ giữ nguyên chữ, không bao giờ chạy). `$count` của list là số bản ghi sau lọc, trước phân trang; ở endpoint khác là số bản ghi của collection theo route (chỉ đếm khi template dùng `$count`). Response được đo trước khi gửi (object dùng chung như bản ghi cha chỉ duyệt một lần) và khi render; quá `MAX_RESOURCE_BYTES` (2 MB) thì 422 `RESPONSE_TOO_LARGE` (gợi ý dùng `?limit`). Số byte đo được cộng vào ngân sách byte của secret.
- **Rate limit:** cửa sổ cố định 1 giây trong bộ nhớ process, kiểm theo thứ tự và chạy trước khi đọc body; vượt bất kỳ mức nào thì 429 `RATE_LIMITED` kèm `Retry-After`. Preflight không bị tính.
  - `MOCK_RATE_LIMIT_PER_IP`: mặc định 30 request/s, IP theo `TRUST_PROXY`, IPv6 gộp /64.
  - `MOCK_RATE_LIMIT_PER_SECRET`: mặc định 60 request/s.
  - `MOCK_WRITE_RATE_LIMIT_PER_SECRET`: mặc định 10 lượt POST/PUT/PATCH/DELETE mỗi giây, vì mỗi lượt ghi giữ khoá project trong một transaction.
  - `MOCK_RESPONSE_BYTES_PER_SECOND`: mặc định 20 MiB body phản hồi mỗi secret mỗi giây. Request bị từ chối khi giây hiện tại đã tiêu hết ngân sách; response bắt đầu trong ngân sách được gửi trọn, nên một giây có thể vượt tối đa một response (2 MB).
  - Chỉ chính xác khi mock runtime chạy một process (PM2 fork); nhiều process thì mỗi process cho đủ mức.
  - Mock runtime đang chạy chung process với dashboard API. Khi tải mock tăng, nên tách nó thành process PM2 riêng (cùng code, chỉ mở cổng 4100) để CPU dùng cho render và đo JSON không làm chậm dashboard; khi đó cache project không còn được dashboard xoá trực tiếp, nên đổi prefix hoặc xoá project có độ trễ tới TTL 60 giây (chưa làm).
- **Hạn mức tháng:** theo **chủ project**, `limitsFor(plan hiệu lực).mockRequestsPerMonth` (Pro hết hạn tính như Free; `null` là không giới hạn). `UsageMeter` đọc tổng tháng (giờ Saigon) của owner một lần, đếm trong bộ nhớ và `$inc` vào `usage_counters` mỗi 5 giây và khi shutdown (trước khi ngắt Mongo). Request đã qua rate limit và trỏ tới project có thật đều được tính (kể cả 404 trong project); request bị từ chối thì không. Hết hạn mức thì 429 `MONTHLY_QUOTA_EXCEEDED`. Khi một lượt `$inc` đưa tổng vượt 80% hoặc 100%, chủ project nhận thông báo `usage.quota` (link `/account`); mỗi lượt `$inc` phủ một khoảng đếm riêng nên mỗi ngưỡng chỉ báo một lần mỗi tháng, kể cả khi nhiều process. Nhiều process thì mỗi process có thể vượt hạn mức tối đa một chu kỳ flush.
- **HTTP:** `Access-Control-Allow-Origin: *` (không bao giờ kèm credentials), preflight trả 204 với các method mock và đúng danh sách header được hỏi (nên `Authorization` dùng được), `Max-Age` 600. Mọi response có `X-Localman-Request-Id`; body là `application/json`. Helmet mặc định trừ `Cross-Origin-Resource-Policy: cross-origin`. Lỗi không lường trước trả 500 `INTERNAL_ERROR` không chi tiết; log chỉ ghi method, 4 ký tự đầu của secret (path có thể chứa secret) và request id (giữ ở `res.locals`, trùng header client nhận), không ghi body.
- **Kiểm chứng:** contract test chạy lại các ví dụ trong wiki nguồn (`contract*.test.ts`), test bảo mật (`security.test.ts`), `pnpm --filter @localman/api load:mock` (MongoDB trong bộ nhớ, 20 giây dưới ngưỡng báo p95, 10 giây vượt ngưỡng báo tỉ lệ 429) và `pnpm --filter @localman/api bench:mock-writes` (60 PATCH song song trên resource 999 bản ghi, báo thời gian, lệnh Mongo và số document đọc về).

## Form quan tâm gói Pro

Module `apps/api/src/modules/feedback/` (collection `feedback`, field `type`; giờ chỉ có `pro_interest`). Không có mail server: form chỉ lưu email để owner liên hệ sau.

- `POST /api/v1/feedback/pro-interest` công khai; có phiên thì gắn `userSub`. Thứ tự kiểm:
  - Rate limit: theo IP (IPv6 gộp theo /64, IPv4-mapped tính như IPv4) 5 lần mỗi 10 phút; người đã đăng nhập còn bị giới hạn theo tài khoản 3 lần mỗi 10 phút (cả hai phải qua). Đếm trong Mongo `rate_limit_windows` theo hash của khoá, tự hết hạn theo cửa sổ (`apps/api/src/lib/rate-limit-windows.ts`, dùng chung với giới hạn lời mời).
  - Honeypot `website`: có giá trị thì trả 201 như thật nhưng không lưu, không báo.
  - Cloudflare Turnstile cho khách khi `TURNSTILE_*` được cấu hình (production bắt buộc). Token phải được giải trên đúng host của `PUBLIC_URL` (bỏ qua với secret thử nghiệm của Cloudflare) và, nếu widget khai `action`, đúng `pro_interest`. Siteverify quá 5 giây hoặc lỗi 5xx thì 503 `TURNSTILE_UNAVAILABLE` (chặn chứ không cho qua); token thiếu hoặc sai thì 400 `TURNSTILE_FAILED`. Bắt buộc `consent: true`.
- `source` thuộc danh sách cố định `PRO_INTEREST_SOURCES` trong `packages/shared`; giá trị lạ được lưu thành `other`.
- Gộp theo email đã chuẩn hoá (unique index một phần trên `type: "pro_interest"`). Mọi lượt gửi được thêm vào `submissions[]` (giữ 20 lượt gần nhất, có cờ `applied`). Câu trả lời của bản ghi chỉ đổi khi cùng danh tính: bản ghi đã gắn tài khoản thì chỉ chính tài khoản đó sửa được (`userSub` không bao giờ bị thay); bản ghi chưa gắn thì khách khác ghi đè được (không phân biệt được khách), còn user đăng nhập chỉ nhận bản ghi đó khi email trùng email đã xác minh ở IdP. `emailMatchesAccount` ghi lại điều kiện xác minh này.
- Sau khi lưu, bot Telegram của Localman báo nền về `OWNER_TELEGRAM_CHAT_ID` (mới, cập nhật hay chỉ lưu lịch sử; nhu cầu, quy mô, nguồn, email che dạng `ng***@gm***.com`; không có tên, ghi chú hay email đầy đủ). Tối đa 10 tin mỗi giờ; tin vượt được đếm và cộng thành "và X lượt khác" vào tin đầu tiên của cửa sổ kế tiếp.
- Admin (`admin.*`, `guard: ownerOnly` theo `OWNER_SUBS`, `GET /users/me` có `isOwner`): thống kê, danh sách lọc theo nguồn, nhu cầu, đã liên hệ, đoạn email, phân trang (item có `emailMatchesAccount` và `submissions`); xuất CSV trả JSON `{ filename, csv }` (registry chỉ trả JSON, và agent MCP cũng đọc được), UTF-8 có BOM, ô bắt đầu bằng `= + - @`, tab hoặc CR được thêm `'` để chống formula injection; đánh dấu đã liên hệ; xoá theo yêu cầu (`dryRun`).

## Cấu hình sản phẩm

Ngoài biến nền tảng, `apps/api/src/config/feature-env.ts` đọc `MOCK_BASE_DOMAIN`, `MOCK_RATE_LIMIT_PER_SECRET`, `MOCK_RATE_LIMIT_PER_IP`, `MOCK_WRITE_RATE_LIMIT_PER_SECRET`, `MOCK_RESPONSE_BYTES_PER_SECOND` (truyền thẳng cho mock app), `OWNER_SUBS`, `OWNER_TELEGRAM_CHAT_ID`, `TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET_KEY`, `TURNSTILE_VERIFY_URL` (xem `.env.example`). Operation được khai báo tĩnh nên đọc các giá trị này qua `config/runtime-settings.ts`, do `main.ts` cài khi khởi động.

## Dữ liệu

MongoDB 7 chạy dạng single-node replica set (`rs0`), vì dữ liệu resource được thay trong transaction. File `docker-compose.yml` dựng sẵn và tự `rs.initiate` ở lần chạy đầu. Test dùng `MongoMemoryReplSet` một node (wiredTiger) chung cho cả lượt chạy, mỗi file test một database.
