# Kiến trúc hệ thống

Monorepo `localman-next` là pnpm workspace gồm `apps/*` và `packages/*`, chạy trên Node ≥ 22 và TypeScript strict (ESM).

## Luồng request của api

```
apps/api/src/main.ts
  ├─ loadEnv()            zod validate biến môi trường, sai thì log fatal và exit 1
  ├─ connectMongo()       không kết nối được thì exit 1 (fail-fast, PM2/Compose tự restart)
  ├─ migrateToTenants()   gắn tenant chính cho document cũ, chờ mọi model dựng xong index (index unique dựng lỗi thì exit 1), bỏ index cũ đã có bản `tenantId` đứng đầu
  ├─ dashboard app :4000  request id + log → tenant của Host (421 nếu không có) → helmet → Localman MCP (/mcp, /.well-known/oauth-protected-resource) → CSRF guard → với route có `bodyLimit`: kiểm phiên (ẩn danh 401 trước khi đọc body) rồi json theo route → json 100kb → /auth/*, /internal/audit-events → /api/v1/openapi.json → no-store + router từ registry → /healthz → 404 → error handler
  ├─ mock app      :4100  request id + log → tenant của Host → helmet (CORP cross-origin, không CSP) → CSP sandbox + nosniff → CORS (preflight 204) → đọc secret → rate limit → json 100kb → mock router → /healthz → 404 → error handler
  └─ TombstoneSweeper     dọn ngay rồi mỗi 10 phút các project xoá dở (xem Projects)
```

- Phần khung dùng chung cho hai server nằm ở `apps/api/src/http/create-base-app.ts`.
- Hai server lắng nghe trên `HOST`: production mặc định `127.0.0.1` (chỉ nginx cùng máy gọi được, không đi vòng qua `limit_req` của nginx), môi trường khác mặc định mọi interface như Node.
- `/healthz` luôn trả 200 kèm trạng thái kết nối DB, kể cả khi Mongo rớt giữa chừng.
- Mọi lỗi trả về dạng `{ "error": { "code", "message", "details"? } }`. Lỗi không lường trước trả 500 `INTERNAL_ERROR`, không lộ stack.
- **Log request** (`http/request-log.ts`): mọi response của cả hai server có header `X-Localman-Request-Id` (UUID, giữ ở `res.locals.requestId`, log lỗi mang cùng id) và một dòng JSON pino `msg: "request"` khi response kết thúc: `requestId`, `method`, `route`, `status`, `ms`, `projectId` nếu biết (`aborted: true` khi client ngắt). `route` là template đã khớp (`/api/v1/projects/:projectId`; không khớp route nào thì `(unmatched)`); mock runtime ghi path thật nhưng che secret (`/m/abcd…/users`, secret trong Host không bao giờ được ghi). Không bao giờ ghi header, cookie, body hay query string.
- SIGTERM/SIGINT chạy các bước của `lib/shutdown-sequence.ts` theo thứ tự, tổng trong ngân sách 10 giây (bước nào còn chạy khi hết ngân sách thì dừng ở đó và thoát mã 1; bước lỗi được log rồi chạy bước sau): (1) dừng hàng đợi gửi ra ngoài (không nhận job mới, lần thử đang chạy bị huỷ và job về `pending`); (2) đóng stream SSE: log trực tiếp và mọi handler MCP (Localman MCP và handler theo request của Hosted Mock MCP, gom ở `McpHandlerRegistry`); từ đó cả hai trả 503 `SHUTTING_DOWN`, kể cả request đang xác thực dở; (3) ghi bộ đếm hạn mức còn chờ; (4) ghi buffer log request; (5) đóng cả hai server (`http/close-server.ts` dọn kết nối keep-alive rảnh mỗi 100 ms; response upstream chậm có thể giữ tới 30 giây, nhưng lúc này hạn mức và log đã được ghi); rồi ghi lần nữa phần sinh ra trong lúc đóng server, dừng sweeper tombstone, chờ thông báo nền và ngắt Mongo.

## Đăng nhập và phiên

Localman không giữ mật khẩu. User đăng nhập ở IdP dùng chung `auth.hoandat.com` (repo `hoandat-auth`, hợp đồng ở `docs/integration-guide.md` của repo đó); Localman là client OIDC confidential `localman-web` (`apps/api/src/modules/auth/`).

- **Đăng nhập:** `GET /auth/login` tạo `state`, `nonce`, PKCE verifier, dựng URL tới IdP (scope `openid profile email telegram`, không `offline_access`, không `resource`, nên access token là opaque và làm được subject của token exchange), rồi mới lưu transaction ở `login_transactions` (TTL 10 phút). Trình duyệt chỉ giữ một handle ngẫu nhiên trong cookie `lm_login` (SameSite=Lax). Giới hạn 20 lần mỗi phút cho mỗi IP, callback có bộ đếm riêng cùng mức (mỗi callback tiêu một transaction); vượt thì 303 về `/?authError=rate_limited`. IdP không phản hồi thì 303 về `/?authError=idp_unavailable`. Cả hai là điều hướng trình duyệt nên không trả JSON.
- **`returnTo` và link nội bộ:** chỉ nhận path bắt đầu bằng một `/`. Path được chuẩn hoá như trình duyệt (dot segment, `%2e`) rồi kiểm lại, nên `/.//evil.com` hay `/%2E%2E//evil.com` (chuẩn hoá thành `//evil.com`) bị chặn và về `/projects`. Luật này nằm ở `http/internal-path.ts`, dùng chung cho `link` của thông báo.
- **Callback:** transaction chỉ bị tiêu khi `state` của callback khớp, nên một callback giả không huỷ được lượt đăng nhập thật đang chờ. Sau đó đổi code (kiểm state, nonce, PKCE), đọc `userinfo` để upsert user (`users`, kèm chat Telegram), tạo phiên mới và đặt cookie `__Host-lm_session` (HttpOnly, Secure, SameSite=Strict, Path=/; trên http dev là `lm_session`). Lỗi thì về `/?authError=access_denied|login_expired|login_failed|idp_unavailable|rate_limited`.
- **Đăng nhập im lặng (SSO):** phiên Localman và phiên IdP là hai cookie riêng, nên trình duyệt đã đăng nhập ở IdP vẫn là khách ở Localman cho tới khi đi qua `/auth/login`. Callback thành công đặt cookie gợi ý `__Host-lm_sso_hint=1` (không HttpOnly để web đọc được, SameSite=Lax, 90 ngày); bấm đăng xuất ở Localman thì xoá nó. Khi `/users/me` trả 401 mà trình duyệt có cookie gợi ý, không có `lm_sso_tried` và trang không mang `?authError=`, web chuyển tới `/auth/login?prompt=none&returnTo=<trang hiện tại>` và giữ trạng thái "loading" (`features/auth/silent-sign-in.ts`). API đặt `__Host-lm_sso_tried` (60 giây, đọc được từ web) **trước** khi gọi IdP và từ chối lượt im lặng thứ hai trong 60 giây đó (303 thẳng về `returnTo`), nên IdP không có phiên hay IdP sập đều không gây vòng chuyển hướng. IdP còn phiên thì quay về đã đăng nhập, không hiện trang nào của IdP; IdP trả `login_required`/`consent_required` hay lỗi khác sau khi đã có transaction thì quay về đúng `returnTo`, không có `authError` (`login_expired` và `rate_limited` xảy ra trước khi biết lượt đó là im lặng nên vẫn hiện như cũ). Chỉ trình duyệt từng đăng nhập Localman mới được thử, nên khách mới và bot (kể cả bot chạy JavaScript) không bị chuyển sang IdP; người chưa từng đăng nhập Localman vẫn phải bấm "Đăng nhập" một lần. Web build gọi API khác origin (`VITE_API_BASE_URL`) không đọc được cookie gợi ý nên không thử.
- **Phiên** (collection `sessions`): `_id` là SHA-256 của giá trị cookie; `sub`, `sid` của IdP, access/refresh/ID token mã hoá chung một blob AES-256-GCM (AAD là id phiên, key từ `SESSION_ENCRYPTION_KEY` có key id để xoay vòng). Hết hạn 30 ngày không dùng, tối đa 90 ngày, giống grant của IdP. Huỷ phiên (đăng xuất, back-channel, refresh bị từ chối) thì xoá luôn các thiết bị Web Push mà phiên đó đã đăng ký.
- **Refresh:** access token còn dưới 60 giây thì refresh ngay khi xử lý request. Refresh token xoay vòng và dùng lại sẽ làm IdP thu hồi grant, nên mỗi phiên chỉ một lượt refresh: request cùng process dùng chung một promise, các process khác nhường nhau qua lease `refreshLockedUntil` trên document phiên. Refresh xong đọc lại `userinfo`. IdP trả `invalid_grant` thì xoá phiên (401).
- **Khi IdP sập (đánh đổi có chủ ý):** lỗi refresh tạm thời không xoá phiên; request vẫn chạy bằng access token cũ tới khi nó hết hạn (15 phút). Sau đó mọi API có scope trả 503 `AUTH_UNAVAILABLE` cho tới khi IdP trở lại, thay vì cho dùng tiếp một phiên mà IdP không còn xác nhận được.
- **Đăng xuất:** `POST /auth/logout` (form) xoá phiên rồi 303 tới `end_session_endpoint` với `id_token_hint`. `POST /auth/backchannel-logout` nhận logout token từ IdP, xác minh bằng JWKS (`iss`, `aud=localman-web`, `typ=logout+jwt`, `iat` trong 2 phút, sự kiện back-channel, không `nonce`, có `sid` hoặc `sub`), huỷ phiên theo `sid` (hoặc mọi phiên của `sub`) rồi mới ghi `jti` vào `logout_token_jtis`, để lượt IdP gửi lại vẫn đăng xuất được nếu bước ghi lỗi.
- **Sự kiện audit:** `POST /internal/audit-events` nhận SET (`application/secevent+jwt`, ES256, `typ: secevent+jwt`, `aud` là URL đầy đủ của endpoint `${PUBLIC_URL}/internal/audit-events`, `iat` không quá 15 phút và `exp` không quá 15 phút sau `iat`, dung sai đồng hồ 30 giây) kèm `Authorization: Basic` so khớp constant-time với `AUDIT_CLIENT_ID`/`AUDIT_CLIENT_SECRET`; thiếu hai biến này thì route trả 404. `jti` (bằng `Idempotency-Key`) lưu ở `audit_events` (30 ngày); sự kiện gửi lại được trả 202 mà không xử lý lại. `method.unlinked` với `method: "telegram"` xoá chat đã lưu ngay; `method.linked` telegram tạm dừng Telegram (`telegram.refreshPendingAt`) cho tới lần đọc `userinfo` kế tiếp (refresh hoặc đăng nhập). `email.reclaimed` xoá email của tài khoản và gỡ các lời mời gắn qua email đó (xem mục Cộng tác viên). Sự kiện khác chỉ được ghi lại.
- **Giới hạn route server-to-server:** `POST /auth/backchannel-logout` và `POST /internal/audit-events` mỗi route 600 lượt mỗi phút mỗi IP (`ipRateLimit`, `http/ip-rate-limit.ts`), chạy trước khi đọc body và trước khi kiểm Basic; vượt thì 429 `RATE_LIMITED` (JSON).
- **Token exchange:** `TunnelTokenExchange` đổi phiên lấy token `aud=https://tunnel.hoandat.com` (tenant khác: `https://tunnel.<domain>`), `scope=tunnels:read` (RFC 8693), cache theo phiên tới gần hết hạn. Module `tunelo` dùng nó để đọc tunnel theo tài khoản (mục "Dữ liệu API client theo user").
- Mọi response `/api/v1/*` có `Cache-Control: no-store`; các route `/auth/*` và `/internal/*` cũng vậy.

## Proxy và IP của client

Localman deploy theo quy ước của server .65: pm2 chạy API, nginx giữ TLS và chạy **cùng máy**. Vì vậy `TRUST_PROXY` mặc định `loopback` (tương đương `127.0.0.1` và `::1`) là đúng: chỉ nginx trên máy được đặt `X-Forwarded-For`, và giới hạn theo IP (`GET /auth/login`) thấy IP thật của client. Giá trị được kiểm lúc khởi động bằng chính `proxy-addr` mà Express dùng: IP/CIDR sai làm API không khởi động. `true` luôn bị từ chối (ai cũng giả được `X-Forwarded-For`); ở production số hop cũng bị từ chối, phải ghi địa chỉ. Nếu chạy sau proxy khác (load balancer, Cloudflare Tunnel, nginx ở máy khác) thì phải đặt `TRUST_PROXY` bằng đúng địa chỉ hoặc CIDR của proxy đó, nếu không mọi request bị tính chung một IP.

## Thông báo

Không có email. `apps/api/src/modules/notifications/` gửi mỗi sự kiện tới các kênh user chọn cho loại sự kiện đó (`notification_preferences`):

- **Trong app** (mặc định bật, tắt được theo từng loại): lưu ở `notifications` (giữ 90 ngày), là dữ liệu của chuông.
- **Web Push** (mặc định tắt): VAPID (`VAPID_*`, tuỳ chọn), subscription theo thiết bị (`push_subscriptions`, endpoint duy nhất, chỉ nhận host của dịch vụ push trình duyệt), gắn với phiên đã đăng ký nó. Phiên kết thúc hoặc hết hạn thì thiết bị không nhận push nữa và bị xoá. Dịch vụ push trả 404/410 thì xoá subscription.
- **Telegram** (mặc định tắt): bot riêng của Localman (`TELEGRAM_BOT_TOKEN`, tuỳ chọn), `chatId` lấy từ `userinfo` của IdP. 429 thì gửi lại theo `retry_after` hoặc backoff luỹ thừa, tối đa 3 lượt và chờ không quá 10 giây; 403 thì đánh dấu kênh chưa kích hoạt cho tới khi chat đổi hoặc user bật lại Telegram trong tuỳ chọn.

`notify()` lưu bản trong app rồi trả về ngay; Web Push và Telegram chạy nền, lỗi chỉ ghi log. Khi tắt server, `drain()` chờ các lượt gửi nền xong. Danh mục sự kiện và schema tham số ở `notification-events.ts` (`NOTIFICATION_PARAMS`); module khác gọi `getNotificationService().notify(sub, { type, params, link })`, không truyền chữ.

**Thông báo thử:** `POST /api/v1/notifications/test` (`notifications.sendTestNotification`, MCP tool `send_test_notification`) gửi loại `notification.test` tới chuông và mọi kênh sẵn sàng, bỏ qua tuỳ chọn theo loại sự kiện, chờ từng kênh rồi trả kết quả theo kênh (`inApp: sent`; `webPush: sent|skipped|failed`; `telegram: sent|skipped|blocked|failed`). Chat Telegram đã bị đánh dấu chặn được xoá `blockedAt` và thử lại (user có thể vừa bấm Start); 403 mới đánh dấu chặn lại và trả `blocked`. Chưa liên kết chat hoặc đang chờ `refreshPendingAt` thì `skipped`. `notification.test` nằm trong `NOTIFICATION_TYPES` nhưng không thuộc `NOTIFICATION_EVENT_TYPES`, nên không có trong tuỳ chọn. Mỗi user 1 lần/phút (`rate_limit_windows`, 429 `RATE_LIMITED`).

**Ngôn ngữ:** user có `locale` (`en`, `zh-CN`, `vi`; chưa chọn thì `en`), đặt bằng `PUT /api/v1/users/me/locale` (`users.setLocale`) và trả trong `GET /users/me`. Bản trong app chỉ lưu `type` + `params`, chữ được render theo `locale` hiện tại của user mỗi lần đọc, nên đổi ngôn ngữ thì thông báo cũ cũng đổi; bản ghi trước khi có i18n không có `params` mà có `title`/`body` tiếng Việt, được trả nguyên như cũ. Web Push và Telegram render theo `locale` của người nhận lúc gửi; nhãn loại sự kiện ở trang tuỳ chọn cũng theo `locale`. Tin báo owner (góp ý, quan tâm Pro, yêu cầu gia hạn dùng thử, dòng "và X lượt khác") theo ngôn ngữ của user có chat Telegram trùng `OWNER_TELEGRAM_CHAT_ID`, nếu không thì của owner đầu tiên trong `OWNER_SUBS` đã chọn ngôn ngữ, còn lại `en`. Chuỗi server ở `apps/api/src/i18n/` (xem [i18n.md](i18n.md#server)).

## Projects và giới hạn gói

Module `apps/api/src/modules/projects/`, operation `mock.*` dưới `/api/v1/projects`: `listProjects` (`GET /projects`), `getProject` (`GET /projects/:projectId`, cùng shape với một item của danh sách, 404 khi không đọc được, không tồn tại hoặc đang xoá), `createProject`, `updateProject`, `deleteProject`, `cloneProject`, `rotateProjectSecret` (`POST /projects/:projectId/rotate-secret`).

- **Project** (collection `projects`): `name`, `prefix`, `secret`, `owner` (`sub`), `quotaSlot`, timestamps. Zod của tên và prefix nằm ở `packages/shared/src/project-schema.ts`, web và api dùng chung. Tên bắt đầu bằng chữ hoặc số, sau đó nhận chữ mọi ngôn ngữ (có tiếng Việt, chuẩn hoá NFC), số, `_`, khoảng trắng, `-` và dấu ngoặc (để bản clone "X (copy)" sửa được mà không phải đổi tên). Prefix theo `^[\w\-/]*$` rồi chuẩn hoá thành `/x/y`, rỗng là không có prefix. Prefix trùng nhau trong cùng owner được phép như mockapi.io, vì mỗi project có subdomain riêng theo secret.
- **Secret** là nhãn DNS của mock runtime (owner xoay được, xem Phân quyền): nanoid 24 ký tự chỉ gồm `a-z0-9` (hostname không phân biệt hoa thường, `_` không hợp lệ trong hostname), khoảng 124 bit, unique index. `mockBaseUrl` = `https://{secret}.{MOCK_BASE_DOMAIN}{prefix}`; domain `localhost…` dùng `http`.
- **Phân quyền:** `project-access.ts` chỉ để lộ `can(user, action, project)` (`read`, `editResources`, `clone`, `update`, `delete`, `manageMembers`) và `accessibleProjectsFilter(user)` cho truy vấn danh sách. Owner làm được mọi việc; collaborator đã accept được `read`, `editResources` (resource và dữ liệu) và `clone`, không sửa/xoá project và không quản lý thành viên. Quyền dashboard đọc từ Mongo mỗi request (không cache), nên rời hoặc bị xoá là mất quyền dashboard ngay. URL mock (secret) là quyền kiểu bearer: ai biết URL đều gọi được mock API, kể cả thành viên đã bị xoá. Muốn chặn hẳn, owner xoay secret bằng `rotateProjectSecret` (chỉ owner, `dryRun` trả số collaborator sẽ được báo): secret mới sinh như lúc tạo project, mục cache của secret cũ bị xoá ngay nên URL cũ trả 404 tức thì, dữ liệu giữ nguyên, các collaborator còn lại nhận thông báo `project.mockUrlChanged`. Không đọc được project thì 404 `NOT_FOUND` để không lộ project tồn tại; đọc được nhưng không có quyền thao tác thì 403 `FORBIDDEN`. View project (danh sách và `getProject`) có `role` và `memberCount` (owner cộng collaborator đã accept).
- **Dữ liệu phụ thuộc:** module khác đăng ký `registerProjectDependent({ kind, count, deleteAll, copy? })` ở `project-dependents.ts`. Xoá project (`dryRun` trả số lượng theo `kind`) đi ba bước, lặp lại an toàn: (1) dưới khoá project (`projects/project-lock.ts`, `inProjectTransaction`) đặt tombstone `deletingAt`; từ đó project coi như đã mất với mọi lượt đọc và ghi (404, không hiện trong danh sách), trừ `DELETE`; (2) gọi `deleteAll` (idempotent) của từng dependent; (3) xoá document project, lúc này slot hạn mức project mới được trả. Bước 2 lỗi thì tombstone ở lại, project vẫn chiếm slot, và `DELETE` lần sau dọn tiếp; ngoài ra `TombstoneSweeper` (`projects/tombstone-sweeper.ts`, chạy lúc khởi động rồi mỗi 10 phút, timer `unref`, dừng khi shutdown) gọi lại đúng `deleteProjectCascade` cho các project có `deletingAt` cũ hơn 5 phút (tối đa 100 mỗi lượt, đọc qua index partial `{ deletingAt: 1 }` với `$exists: true`; project sống không lưu field này nên index chỉ chứa tombstone, trừ project cũ còn lưu `deletingAt: null`), nên lượt xoá đứt giữa chừng do lỗi hay restart không giữ slot mãi. Mọi bước đều idempotent nên sweeper chạy song song với một `DELETE` lặp lại trên cùng project vẫn an toàn. Lượt ghi resource chạy đua với bước 1 hoặc commit trước (rồi bị bước 2 dọn), hoặc xung đột trên khoá, chạy lại và nhận 404, nên không còn dữ liệu mồ côi. Tombstone cũng là nền cho thùng rác 30 ngày (`trashDays`) sau này. Clone tạo project mới (secret mới, tên "X (copy)" cắt theo code point cho vừa giới hạn, tính vào hạn mức của người clone) rồi gọi `copy` của từng dependent; `copy` lỗi thì xoá bản clone dở. Dependent không có `copy` (thành viên) không đi theo bản clone.
- **Hạn mức project** (`billing/plan-guard.ts`): chỉ đếm project user sở hữu, theo `limitsFor(plan).projects`; vượt thì 403 `PLAN_LIMIT_REACHED` kèm `details: { limit: "projects", max, used }`. Pro có `planExpiresAt` đã qua thì tính như Free (cả ở `GET /users/me`). Chống tạo song song vượt hạn mức không cần transaction: mỗi project giữ một `quotaSlot`, unique index `(owner, quotaSlot)`. Lượt tạo đọc các slot đang dùng, từ chối khi đủ hạn mức, rồi lấy slot trống nhỏ nhất; các lượt đọc cùng dữ liệu chọn cùng một slot nên chỉ một lượt insert thắng, các lượt khác đọc lại và kiểm lại.
- **Bộ đếm tháng** (`billing/usage-counter-model.ts`, collection `usage_counters`): một document theo `ownerSub` + `yyyymm` (tháng theo lịch Asia/Saigon) với `mockRequests` và `proxyRequests`; `incrementUsage()` tăng nguyên tử và trả tổng mới cho mock runtime và proxy. `GET /api/v1/account/usage` trả gói đang áp dụng, project đã dùng và hai bộ đếm tháng so với hạn mức; `max: null` là không giới hạn (`Infinity` được map tường minh).
- **Hoạt động theo project:** `lastRequestAt` và `mockRequests` (tổng) trên document project, do mock runtime cộng dồn theo lô (xem Hạn mức tháng ở Mock runtime), chỉ trên project còn sống và không đổi `updatedAt`.
- **Dọn project bỏ hoang:** `pnpm --filter @localman/api cleanup:abandoned [--days 90] [--apply]` (`apps/api/scripts/cleanup-abandoned-projects.ts`, logic ở `projects/abandoned-projects.ts`). Chọn project còn sống của owner có gói hiệu lực Free (Pro hết hạn và user không tồn tại tính là Free) mà mốc hoạt động cuối cũ hơn N ngày. Mốc hoạt động (`projects/project-activity.ts`) là giá trị lớn nhất của `lastRequestAt`, `updatedAt` của project và `updatedAt` mới nhất trong các resource của project; không có gì mới hơn thì là `createdAt`. Nhờ vậy project vừa sửa project hay resource trên dashboard mà chưa nhận request mock nào không bị coi là bỏ hoang. Mongo lọc trước theo `lastRequestAt` và `updatedAt` của project, rồi mới gộp `updatedAt` của resource cho danh sách rút gọn đó. Mặc định chỉ in danh sách (dry run: `projectId`, `owner`, `lastActivityAt`, `lastActivitySource` là `created` | `projectEdit` | `mockRequest` | `resourceEdit`, `lastRequestAt`, `createdAt`, `resources`), `--apply` mới xoá: tính lại mốc hoạt động của từng project ngay trước khi xoá rồi đi qua `deleteProjectCascade` như `DELETE`. Script đọc env bằng `parseEnv` như API, log JSON bằng pino; exit 1 khi có lượt xoá lỗi, 2 khi sai tham số hay env. Chạy ở process riêng nên cache secret của API có thể trả project đã xoá thêm tối đa 60 giây (404 cho mọi route vì resource đã mất). `lastRequestAt` chỉ được ghi từ khi có tính năng này: project cũ chưa nhận request nào kể từ đó bị tính theo lần sửa cuối hoặc `createdAt`, nên lần đầu chạy luôn xem dry run.
- **Gán gói tạm thời** (chưa có billing): `MONGO_URI=… pnpm --filter @localman/api set-user-plan --username <u> --plan pro --expires YYYY-MM-DD` (`--expires` tính hết ngày đó theo giờ Saigon, ngày đã qua phải thêm `--force`; `--plan free` xoá hạn). Script chỉ in `sub`, `username`, `plan`, `planExpiresAt`.

## Dùng thử Pro (tự động)

Chưa thương mại ([ADR-0002](decisions/0002-no-commercial-ui-automatic-pro-period.md)): web không hiện gói, giá hay dùng thử; người dùng chỉ thấy "hạn mức mở rộng" tới ngày nào ở trang tài khoản. Pro được mở dưới dạng dùng thử 30 ngày, mỗi tài khoản một lần (`apps/api/src/modules/trial/`, hằng số ở `packages/shared/src/trial-constants.ts`). Tài khoản chưa từng dùng thử và không đang Pro tự được bắt đầu khi đăng nhập hoặc khi phiên được làm mới (`autoStartTrial`, gọi cuối `syncUserFromUserInfo`; một lệnh cập nhật có điều kiện nên chạy đúng một lần; lỗi chỉ được log, không làm hỏng đăng nhập, lần làm mới sau thử lại). Tài khoản chưa từng dùng thử mà admin hạ về Free cũng được tự cấp lại ở lần làm mới phiên kế tiếp (ghi ở ADR-0002). Dùng thử chỉ là `plan: "pro"` + `planExpiresAt`, nên mọi chỗ đọc gói qua `effectivePlan` (hạn mức, mock runtime, proxy) tự coi người hết hạn là Free, không cần job hạ gói. Mock runtime cache gói của owner theo secret 60 giây, nên bắt đầu hay gia hạn dùng thử có hiệu lực ở hạn mức mock trễ tối đa chừng đó (ngày hết hạn vẫn được so mỗi request).

- **Trạng thái** (`trialStateOf`, trả trong `GET /users/me` ở field `trial`): `available` khi chưa có `users.trialStartedAt` (kể cả người được owner cấp Pro), `active` khi gói hiệu lực là Pro, `ended` khi không còn; `endsAt` là `planExpiresAt`. Kèm `extensionRequest` là yêu cầu gia hạn mới nhất (`pending`, `approved`, `declined`) hoặc `null`.
- **Bắt đầu tay** (web không còn gọi, giữ cho sau này): `POST /api/v1/users/me/trial` (`users.startTrial`) đặt `trialStartedAt`, `plan: "pro"`, `planExpiresAt` = hết ngày Saigon 30 ngày sau, trả shape của `GET /users/me`. Lượt ghi chỉ khớp user chưa có `trialStartedAt`, nên bấm hai lần cùng lúc chỉ bắt đầu một lần. 409 `TRIAL_ALREADY_USED` khi đã từng dùng thử, 409 `ALREADY_PRO` khi đang Pro do owner cấp.
- **Xin gia hạn** (web không còn form; gia hạn do admin quyết): `POST /api/v1/users/me/trial/extension` (`users.requestTrialExtension`, 201) với `reason` 1–500 ký tự (đã trim), khi đang dùng thử hoặc trong 7 ngày sau khi hết (ngoài ra 409 `TRIAL_NOT_EXTENDABLE`); 5 lượt mỗi ngày mỗi tài khoản (`rate_limit_windows`, 429 `RATE_LIMITED`). Collection `trial_extension_requests`: unique partial `{ userSub, status }` chỉ trên `pending` (yêu cầu thứ hai đang chờ bị 409 `EXTENSION_PENDING`, kể cả khi gửi đồng thời), `{ userSub, requestedAt }` cho `GET /users/me`, `{ status, requestedAt }` cho trang admin. Owner (`OWNER_SUBS`) nhận `trial.extension.requested` (chuông, Web Push/Telegram theo tuỳ chọn; loại này ẩn khỏi tuỳ chọn của người không phải owner) và tin Telegram về `OWNER_TELEGRAM_CHAT_ID` (throttle kind `trial.extension` như tin báo owner khác). Chỉ tên hoặc username người xin được gửi đi, lý do chỉ hiện ở trang admin, không vào log hay tin báo.
- **Admin** (`guard: ownerOnly`): `GET /admin/trial-extensions?status=pending|all&cursor` (mới nhất trước, 50 mỗi trang, `nextCursor`), `POST /admin/trial-extensions/:requestId/approve` (Pro tới hết ngày Saigon 30 ngày sau mốc muộn hơn giữa bây giờ và hạn hiện tại; user nhận `trial.extension.approved`), `…/decline` (user nhận `trial.extension.declined`), cả hai 409 `EXTENSION_DECIDED` khi đã quyết (chỉ một lượt thắng khi hai owner bấm cùng lúc; duyệt mà gia hạn lỗi thì yêu cầu trở lại `pending`), và `POST /admin/users/:sub/extend-trial` `{ days: 1..90 }` gia hạn thẳng cho bất kỳ user nào (404 `NOT_FOUND`, 409 `PLAN_HAS_NO_EXPIRY` với Pro không có hạn; yêu cầu đang chờ giữ nguyên). Gia hạn ghi có điều kiện trên giá trị gói vừa đọc nên hai lượt đồng thời đều được cộng. Mỗi thao tác ghi log có cấu trúc (`sub`, `requestId`, `by`, `endsAt`). Mọi operation dùng thử miễn MCP.
- **Nhắc hạn:** `TrialReminderJob` (`trial-reminders.ts`, chạy lúc khởi động rồi mỗi giờ, timer `unref`, dừng ở bước `background` của shutdown trước khi drain thông báo) tìm user có `trialStartedAt` và `planExpiresAt` từ 7 ngày trước tới 7 ngày sau (index partial `{ planExpiresAt: 1 }` theo `trialStartedAt`), gửi mốc muộn nhất đã tới (câu trung tính, không nhắc gói hay gia hạn): `trial.ending` khi còn ≤ 7 ngày và khi còn ≤ 1 ngày (`daysLeft`, `endsOn`), `trial.ended` khi đã qua hạn (tới 7 ngày sau). Mỗi mốc được giữ chỗ trên user trước khi gửi (`trialNotices.<mốc>` = hạn mà nó báo, chỉ khớp khi đang giữ hạn khác), nên mỗi mốc gửi đúng một lần mỗi hạn kể cả nhiều process; gia hạn đổi hạn nên các mốc được gửi lại theo hạn mới; gửi lỗi thì trả chỗ cho lượt sau.
- **Sau khi hết hạn:** không xoá hay tạm dừng gì; chỉ lượt tạo mới bị chặn bằng 403 `PLAN_LIMIT_REACHED` như mọi user Free. `GET /api/v1/account/usage` có `overLimits: [{ limit: "projects" | "resources", used, max }]`, các hạn mức của gói hiệu lực mà số đang sở hữu vượt quá (lớn hơn hẳn `max`).

## Cộng tác viên và magic link

Module `apps/api/src/modules/collaborators/`, operation `collab.*` (toolset MCP `collab`, không thuộc toolset OAuth của Localman MCP): `listCollaborators`, `lookupInvitee`, `inviteCollaborator`, `removeCollaborator` dưới `/api/v1/projects/:projectId/collaborators`; `getMagicLink`, `rotateMagicLink`, `revokeMagicLink` ở `/api/v1/projects/:projectId/magic-link`; `mock.previewInvite`, `mock.acceptInvite` ở `/api/v1/invites/{preview,accept}` (token nằm trong body, không bao giờ trong URL của API; miễn MCP vì chỉ người được mời mở trên trình duyệt).

- **Trần thành viên:** `limitsFor(gói hiệu lực của owner).membersPerWorkspace` (Free 3, Pro 10), tính owner, collaborator đã accept và lời mời còn hạn. Lời mời hết hạn không giữ chỗ, vẫn hiện cho owner với `status: "expired"` (xoá tự động 30 ngày sau hạn); magic link không giữ chỗ, trần kiểm lúc tham gia. Vượt thì 403 `PLAN_LIMIT_REACHED` với `details: { limit: "members", max, used }` (web mở modal gói với nguồn `plan_limit_members`). Hạ gói giữ nguyên quyền của mọi thành viên hiện có; chỉ lời mời mới, accept lời mời đang chờ và tham gia qua magic link bị chặn cho tới khi số chỗ xuống dưới trần. Mọi lượt ghi (mời, accept, tham gia, tạo magic link) chạy trong `inProjectTransaction`: hai lượt cùng project ghi chung document khoá nên một lượt chạy lại trên kết quả của lượt kia, không thể cùng lọt trần; project đã có tombstone thì 404.
- **Mời** (chỉ owner): username (`@` tuỳ chọn) hoặc email, khớp chính xác không phân biệt hoa thường, không tìm theo tiền tố. Email gắn vào tài khoản có email đó đã được IdP xác minh; nếu không có, chỉ gắn khi đúng một tài khoản chưa xác minh dùng email đó (nhiều hơn một thì lời mời chỉ gắn email). Khớp tài khoản thì gắn `inviteeUserId` và gửi thông báo `project.invitation` (trong app, Web Push, Telegram theo tuỳ chọn) kèm link; email chưa có tài khoản thì gắn `inviteeEmail` (lowercase), owner tự gửi link. Không có lời mời không gắn ai. Thẻ tài khoản khớp chỉ có username, tên, avatar, email đã che và `emailVerified` để owner nhận ra tài khoản giả. Mời bản thân trả 400 `CANNOT_INVITE_SELF`, mời thành viên 409 `ALREADY_MEMBER`, username không tồn tại 404 `INVITEE_NOT_FOUND`, đều không kèm thông tin tài khoản. `lookupInvitee` và `inviteCollaborator` dùng chung ngân sách 20 lượt mỗi giờ mỗi owner (`inviteRateLimit`, 429 `RATE_LIMITED`) để không thành công cụ dò tài khoản. Mời lại cùng người hoặc cùng email thì cấp token và hạn mới trên dòng cũ nhất (danh tính dựng lại theo lần mời mới), link cũ hết hiệu lực. Thành viên từng được mời ở một email mà nay không còn dùng email đó không bị coi là người được mời lại.
- **Token:** 32 byte ngẫu nhiên (base64url), chỉ lưu SHA-256, trả về đúng một lần (`inviteLink` hay `link`, dạng `/invite/:token` cho cả hai loại), TTL 7 ngày. Lời mời dùng một lần; magic link dùng lại được, mỗi project tối đa một link (tạo mới thay hash, link cũ ngừng ngay; thu hồi đặt `revokedAt`). `getMagicLink` chỉ trả trạng thái `none | active | expired | revoked`, hạn và thời điểm tạo.
- **Accept:** preview và accept đều cần đăng nhập và bị giới hạn 30 lượt mỗi 10 phút mỗi tài khoản, 60 mỗi IP (`inviteTokenRateLimit`). Lỗi token tách mã: 404 `INVITE_NOT_FOUND` (không có, đã bị thay, project đã xoá), 410 `INVITE_EXPIRED` (`details.expiresAt`), 410 `INVITE_USED`, 410 `INVITE_REVOKED`. Project lấy từ token đã lưu, không từ request, nên token chỉ dẫn vào đúng project của nó. Điều kiện của lời mời: gắn tài khoản thì chỉ tài khoản đó (403 `NOT_INVITEE`); gắn email thì chỉ tài khoản có email được IdP xác minh qua Google/GitHub trùng email đó sau khi lowercase (email chưa xác minh chỉ trùng chữ: 403 `EMAIL_NOT_VERIFIED`). Magic link nhận mọi người đã đăng nhập. Owner và thành viên nhận `alreadyMember: true` mà không đổi gì. Accept hay tham gia thì các dòng chờ khác của người đó (gắn tài khoản, hoặc chưa gắn mà trùng email đã xác minh của họ) được gộp vào, trả lại chỗ. Preview trả `kind`, project, người mời, hạn, email mời đã che, `eligible` và `reason` (`NOT_INVITEE`, `EMAIL_NOT_VERIFIED`, `ALREADY_MEMBER`, `MEMBER_LIMIT`, `REMOVED_BY_OWNER`).
- **Danh sách và rời:** owner thấy mọi dòng kèm email mời; collaborator chỉ thấy owner và thành viên đã accept, không có email. Owner xoá được mọi dòng; collaborator chỉ xoá dòng của mình (rời project).
- **Thành viên bị owner gỡ:** khi owner xoá một thành viên đã accept, cùng transaction khoá project ghi dấu vào `member_removals` (`projectId`, `userSub`, `removedBy`, `removedAt`; unique `(projectId, userSub)`, `member-removal-model.ts`). Magic link từ chối người có dấu: preview trả `eligible: false`, `reason: "REMOVED_BY_OWNER"`, accept trả 403 `REMOVED_BY_OWNER` (kiểm lại trong transaction tham gia). Chỉ khi người đó accept một lời mời mới của owner thì dấu mới bị xoá; huỷ lời mời không xoá dấu. Thành viên tự rời thì không có dấu. Dấu không giữ chỗ và không hiện trong danh sách.
- **Email bị chiếm lại:** sự kiện audit `email.reclaimed` (tài khoản khác ở IdP đã xác minh email này) xoá email khỏi bản sao user, đặt `emailVerified: false`, và gỡ `inviteeUserId` khỏi các lời mời đang chờ đã gắn tài khoản đó qua email; lời mời vẫn gắn email nên chủ email đã xác minh accept được.
- **Index:** token, `(projectId, inviteeUserId)` và `(projectId, inviteeEmail)` là unique partial theo `$exists` (planner dùng được cho truy vấn bằng), thêm `(projectId, status)` cho đếm chỗ và `memberCount`; `users.username` và `users.email` có index collation `en` strength 2 (`CASE_INSENSITIVE_COLLATION`). `users.username` là bản sao từ IdP nên không unique: mời theo username mà khớp hai tài khoản thì 409 `AMBIGUOUS_USERNAME` (mời bằng email), không gắn bừa vào một tài khoản.
- **Project dependents:** `collaborators` và `magicLinks` (đếm và xoá, không `copy`): xoá project xoá cả thành viên, lời mời, dấu gỡ thành viên và magic link; bản clone không có thành viên.

## Workspace, vai trò và chia sẻ phần tử

Bảng quyền nằm ở `@localman/shared/access` (`packages/shared/src/access-permissions.ts`), chép từ bảng "Roles and permissions" của Postman. API quyết định theo bảng này, web đọc nó để ẩn hoặc khoá nút. Mọi operation dưới đây thuộc toolset MCP `sharing`. UI nằm sau cờ `workspaces` của web.

- **Workspace** (`apps/api/src/modules/workspaces/`, `/api/v1/workspaces…`):
  - Mỗi user có đúng một workspace cá nhân, tạo khi dùng lần đầu, bảo đảm bằng unique partial index.
  - Workspace team có thành viên Admin, Editor hoặc Viewer (`workspace_members`). Trần số thành viên là `membersPerWorkspace` theo gói của chủ (`ownerId`); số workspace team mỗi người tạo bị giới hạn bởi `teamWorkspaces` (Free 1).
  - Lời mời theo username, email hoặc link dùng một lần dùng chung quy tắc token và người nhận với lời mời project (`access/invite-addressee.ts`). Preview và accept ở `/workspace-invites/{preview,accept}`, token đi trong body.
  - Admin cuối cùng không hạ vai trò, không bị xoá và không rời được (409 `LAST_ADMIN`). Chủ rời đi thì quyền chủ chuyển cho Admin cũ nhất, kể cả khi người đó vượt hạn mức (`workspace-ownership.ts`).
- **Vai trò trên phần tử** (`apps/api/src/modules/access/`): collection và environment đăng ký adapter (`element-adapters.ts`); danh sách phần tử của người ngoài workspace đi qua `collectSharedElements` (`shared-elements.ts`).
  - Vai trò hiệu lực là vai trò mạnh hơn giữa vai trò suy từ workspace (Admin và Editor thành Editor, Viewer thành Viewer) và share riêng (`element_roles`). Share chỉ nâng, không hạ, và không chiếm ghế thành viên.
  - Không có quyền thì 404, có quyền xem mà thiếu quyền hành động thì 403.
  - Phần tử trong workspace cá nhân không chia sẻ được (409 `PERSONAL_WORKSPACE`). Share theo email chỉ gắn vào tài khoản đã xác minh email đó.
- **Request access:**
  - Luôn trả `{ status: "sent" }` dù phần tử có tồn tại hay không, giới hạn 20 lượt mỗi giờ. Gửi lại với vai trò mạnh hơn thì nâng yêu cầu đang chờ.
  - Editor của phần tử nhận thông báo `access.requested` (tối đa 50 người). Approve phải gửi kèm vai trò đã thấy; yêu cầu đã đổi thì trả 409 `REQUEST_CHANGED`.
- **Link phần tử:** "Copy link" và link trong thông báo share trỏ tới `/elements/:type/:id` (folder/request thêm `?node=<nodeId>`). Đọc được phần tử thì web chọn workspace của nó (chỉ khi người dùng là thành viên; người được share riêng giữ workspace hiện tại, trang phần tử có nhãn "Shared with you") rồi chuyển tới `/api-client` với navigation state chỉ chứa id (đọc một lần rồi xoá), workbench mở trang collection, folder, request đã bind hoặc environment (environment chỉ khi cờ `environments` bật). Không có quyền thì hiện form xin quyền.
- **Move:** cần Admin hoặc Editor ở workspace nguồn và quyền `addElements` ở workspace đích. Không chuyển từ workspace team về workspace cá nhân. Share riêng đi theo phần tử.
- **Project mock** không có workspace: `project-access.ts` quyết định theo `MOCK_PROJECT_PERMISSIONS` (owner là Editor có quyền quản lý, collaborator là Editor không quản lý).
- **Thông báo mới:** `workspace.invitation`, `element.shared`, `access.requested`, `access.resolved`. Item thông báo `access.requested` có `accessRequest: { id, status, role }`.

## Collections của API client

Module `apps/api/src/modules/collections/`, operation `client.*` (toolset MCP `client`). Kiểu, schema và hàm chuyển đổi nằm ở `@localman/shared/api-client` (`collections/`). Cờ web `workspaces` (cùng `apiClient`) bật UI.

- **Lưu trữ:** gốc collection (`collections`: workspace, mô tả Markdown, auth, scripts, variables) và từng folder/request là một bản ghi (`collection_nodes`) có `parentId` và `order` là khoá fractional index trong folder cha. Kéo thả chỉ ghi lại node bị kéo. Các thao tác ghi node chạy dưới khoá workspace, để hai lượt move chéo nhau không lách được kiểm tra vòng. Giới hạn: 2000 node và 20 MiB mỗi collection (đếm dồn trên gốc, trả 413 `COLLECTION_TOO_LARGE`), folder sâu tối đa 64 cấp, 1000 collection còn sống mỗi workspace.
- **Quyền:** mọi route đi qua `requireElement("collection", …)` theo `COLLECTION_PERMISSIONS`. Tạo collection cần `addElements` của workspace. Adapter `collection` của phase 11 giúp share, request access và move hoạt động với collection thật.
- **Kế thừa khi gửi:** `requestContext` trả auth gần nhất (folder rồi collection), danh sách script theo thứ tự collection, folder ngoài vào trong, request, cùng biến của collection.
- **Import/export Collection v2.1:** round-trip không mất field với mọi thứ đợt A lưu. Kiểm bằng JSON Schema chính thức v2.1.0 (fixture trong `packages/shared/src/api-client/export/__fixtures__`). Thiết lập v2.1 không có chỗ (`timeoutMs`, `sendClientIp`, `route`) đi trong khoá `_localman`. Export luôn để trống giá trị biến secret. Qua API, ai xem được collection đều nhận giá trị biến và credential của auth; cờ `secret` chỉ để che trên UI, còn việc để trống chỉ áp cho file rời khỏi Localman và cho các đường [chia sẻ công khai](#chia-sẻ-công-khai).
- **Thùng rác:** xoá collection (có request thì phải gửi `confirm: "delete"`) đặt `deletedAt` và `deletedBy`. Xoá workspace team cũng chuyển mọi collection trong đó vào thùng rác, trong cùng transaction. Quyền restore và xoá vĩnh viễn theo vai trò hiện tại. Khi workspace gốc còn, chỉ Admin hoặc Editor hiện tại của nó làm được; restore sang workspace khác phải qua luật move. Khi workspace gốc đã xoá, người xoá hoặc những người là Admin/Editor lúc xoá (danh sách ghi lại lúc chuyển vào thùng rác) làm được. Xoá vĩnh viễn xoá luôn node, favorite, `element_roles` và `access_requests`. Job dọn xoá vĩnh viễn sau `trashDays` (30 ngày cho mọi gói).
- **Tab gắn với request:** draft của tab (`client_drafts`) có `source { collectionId, nodeId }`; gửi `null` để bỏ liên kết.
- **Example:** node loại `example`, con của một node request trong cùng collection, không có con. Node này chứa request gốc và response đã lưu; body tối đa `EXAMPLE_BODY_MAX`, vượt thì trả 413 `EXAMPLE_TOO_LARGE`. Export v2.1 ghi example vào `response[]`.
- **Tag và status:** tối đa 10 tag, mỗi tag 64 ký tự, lưu lowercase, không trùng lặp, bắt đầu và kết thúc bằng chữ hoặc số. Status là một preset (stable, in-development, in-review, deprecated) hoặc tên tuỳ chỉnh 2–64 ký tự kèm một emoji. Kiểm tra nằm ở `collections/collection-tags.ts` (dùng chung cho API và import). Export ghi tag và status trong `_localman`.
- **Changelog:** mỗi lượt ghi nội dung tạo một revision (JSON Patch xuôi và ngược) trong cùng transaction. Các thay đổi liên tiếp của cùng tác giả nằm trong cửa sổ 5 phút tính từ thay đổi đầu được gom thành một session (`CHANGELOG_SESSION_WINDOW_MS`); một trang được kéo dài tới đầu session chứa bản ghi cũ nhất, nên session không bị cắt ở ranh giới trang (trang có thể dài hơn 100 bản ghi). Editor ẩn hoặc hiện được diff; diff đã ẩn vẫn hiện với Editor và Admin kèm ghi chú, Viewer không tải được. "Restore to this change" dựng lại trạng thái ngay sau revision đó bằng cách áp ngược các patch, rồi ghi kết quả thành một revision mới; lịch sử không bao giờ bị xoá. Mỗi collection giữ tối đa 2000 revision hoặc 20 MiB patch, cắt từ cũ nhất; restore về revision đã bị cắt trả 409 `REVISION_UNAVAILABLE`; revision bị cắt vẫn để lại một stub để phân biệt với id lạ (404 `REVISION_NOT_FOUND`). Thay đổi có patch vượt 4 MiB chỉ lưu metadata; dry run và response của xoá node, xoá hàng loạt và restore trả `irreversible: true` khi thao tác không hoàn tác được. "Hide diff" chỉ ẩn diff của chính thay đổi đó, không xoá dữ liệu khỏi lịch sử. Move sang workspace khác và việc xoá workspace không ghi revision, vì nội dung không đổi.
- **Xoá hàng loạt:** `bulk-delete` node (1–200 node) và `bulk-trash` collection (1–100), đều chạy trong một transaction theo kiểu được hết hoặc không gì cả, và có dry run.
- **Liên kết:** gốc collection lưu `mockProjectId` (ghi khi tạo từ mock project), `linkedEnvironmentId` (Editor chọn; `null` là đã chọn "không có") và `sharedEnvironmentId` (ghi khi share collection kèm một environment cùng workspace; ghi lỗi chỉ log, share vẫn thành công). Detail trả `mockProject` và `relatedEnvironment` (`source: linked | shared`, environment Editor chọn thắng); phần tử đã xoá, khác workspace hoặc người gọi không đọc được thì trả `null`, không lộ tên. Liên kết không ghi changelog.
- **Biến collection, giá trị local:** khi cờ `environments` bật, tab Variables có cột giá trị local của người xem (`client.get/setCollectionLocalValues`); Viewer chỉ sửa giá trị local.

## Comment và watch

Module `apps/api/src/modules/comments/` và `apps/api/src/modules/watch/`, operation `client.*` (toolset MCP `client`, cùng chỗ với collections, nên agent nối qua Localman MCP bằng OAuth dùng được với scope `client:*` có sẵn; toolset `collab` giữ việc quản lý thành viên project, ngoài tầm OAuth). Mọi operation đều có tool. Kiểu và giới hạn ở `@localman/shared/api-client` (`collections/comment-model.ts`). Cờ web `comments` (cần `workspaces`). Chạy được ở workspace team của gói Free; fork, merge và pull request là đợt sau của phase 14.

- **Comment:** `collection_comments`, mỗi comment một bản ghi, gắn với collection (`nodeId: null`) hoặc một folder, request, example của nó. Comment đầu mở thread (`threadId` bằng chính `_id`) và mang anchor cùng trạng thái resolve; trả lời trỏ về nó. Body Markdown tối đa `COMMENT_BODY_MAX`, mỗi collection tối đa `COMMENTS_PER_COLLECTION_MAX` comment (409 `COMMENT_LIMIT`). Quyền theo `COLLECTION_PERMISSIONS`: `comment` cho mọi vai trò (Viewer comment được), `resolveComments` cho Editor (tác giả thread luôn resolve được thread của mình). Chỉ tác giả sửa; tác giả hoặc Admin của workspace xoá (Admin không sửa được); xoá comment đầu là xoá cả thread. Reaction là tập cố định `COMMENT_REACTIONS`, lưu theo khoá bằng `$addToSet`/`$pull`.
- **Comment inline:** anchor gồm phần của request (`url`, `params`, `headers`, `body`, `preScript`, `postScript`; folder và collection chỉ có hai phần script), với params/headers thêm `rowId` và ô `key`/`value`, cùng offset và đoạn chữ đã chọn (`quote`). Lúc tạo, đoạn chữ phải đúng ở vị trí đó trong bản đã lưu (400 `ANCHOR_MISMATCH`). Lúc đọc, thread "outdated" khi vị trí đó không còn đúng đoạn chữ ấy. Web chỉ cho comment inline khi tab trùng bản đã lưu.
- **@mention và thông báo:** `@username` trong body báo `comment.mentioned` cho người mở được collection; trả lời báo `comment.replied` cho những người đã viết trong thread, trừ người đã được nhắc trong chính trả lời đó. Người được báo lưu ở `mentions`, nên sửa comment chỉ báo người mới được nhắc. Link thông báo là `/elements/collection/:id?node=…&comment=…`; web mở phần tử rồi mở panel Comments ở đúng thread.
- **Watch:** `collection_watches` (`{collectionId, userId, lastSeq}`), chỉ cho collection của workspace team (409 `WATCH_UNAVAILABLE`). Bắt đầu theo dõi thì `lastSeq` là revision hiện tại. Job `WatchDigestJob` chạy mỗi phút theo từng tenant: với collection còn sống có revision mới, gửi mỗi người theo dõi một `collection.changed` tổng hợp số thay đổi và số người sửa, bỏ thay đổi của chính họ. Job đọc changelog thay vì móc vào từng đường ghi, vì lượt ghi chạy trong transaction có thể chạy lại, và để gộp nhiều lần lưu thành một thông báo. Người không còn quyền với collection bị xoá khỏi danh sách theo dõi. Purge collection xoá comment và watch của nó.

## Fork, pull và merge

Module `apps/api/src/modules/version-control/`, operation `client.*` (toolset MCP `client`). Kiểu ở `@localman/shared/api-client` (`collections/fork-model.ts`). Cờ web `forks` (cần `workspaces`), cổng server `FORKS_ENABLED`. Chỉ gói Pro (`forkPrPublic`, 403 `PLAN_FEATURE_UNAVAILABLE`).

- **Liên kết fork:** `forks` (`kind` collection hoặc environment, `sourceId`, `forkId`, `label`, `pairs`, `base`). Fork là bản sao có id riêng; `pairs` ghép id node nguồn với id node fork. Gốc chung để merge là snapshot nội dung hai bên đang đồng ý, lưu lúc fork và thay sau mỗi lần pull hoặc merge, không dựng lại từ changelog (changelog bị cắt và có revision không giữ patch). Snapshot của collection lưu mỗi node một bản ghi trong `fork_base_nodes` (gốc collection nằm trên bản ghi fork), để không chạm giới hạn 16 MB của một document.
- **Merge ba chiều** (`three-way-merge.ts`, hàm thuần): ghép theo id node hoặc key biến, không theo vị trí; so từng field dạng JSON, sâu thêm một tầng ở `draft`, `request`, `response`, `scripts`. Hai bên cùng đổi một field khác nhau là xung đột (`<key>:<path>`); một bên xoá còn bên kia sửa cũng là xung đột (`<key>`). Thứ tự anh em đụng nhau thì lấy phía mang thay đổi tới, không báo xung đột. Sau merge, cây được sửa cho hợp lệ: node mất folder lên gốc, example mất request bị bỏ, vòng lặp do di chuyển ở hai phía bị cắt.
- **Pull** (Editor của fork): thay đổi của nguồn vào fork; node mới của nguồn nhận id fork và cặp mới; nguồn thành gốc mới. **Merge** (Editor của nguồn): thay đổi của fork vào nguồn; node mới của fork nhận id nguồn; fork thành gốc mới. `mergeAndUpdate` (cần Editor ở fork) merge rồi pull ngược; `mergeAndDelete` merge rồi chuyển fork vào thùng rác (environment thì xoá hẳn). Mỗi lần pull hoặc merge là một mục changelog (`pull`, `merge`) ghi qua cùng bộ ghi với "restore to this change" (`collection-state-write.ts`), nên restore được. Xung đột chưa chọn trả 409 `MERGE_CONFLICTS`.
- **Quyền:** Viewer của nguồn chỉ fork vào workspace cá nhân (403 `FORK_TARGET_NOT_ALLOWED`); người khác fork vào workspace mình là Admin hoặc Editor. Fork của fork được phép. Nguồn bị xoá thì fork ở lại, báo nguồn không còn, pull và merge trả 404 `FORK_SOURCE_UNAVAILABLE`. Purge fork xoá liên kết và snapshot của nó.
- **Environment:** merge biến theo key và tên, màu. Giá trị secret không bao giờ đi theo pull hay merge (mỗi bên giữ giá trị của mình); fork chép giá trị secret chỉ cho Editor của nguồn, như duplicate. Pull và merge ghi biến cùng tên, màu trong một lần, chỉ khi environment chưa đổi kể từ lúc đọc (409 `ENVIRONMENT_CHANGED`).
- **Pull request** (chỉ collection; `pull_requests`, `pull-request-*.ts`): Editor của fork mở PR vào nguồn, chọn người duyệt trong các Editor của nguồn (400 `INVALID_REVIEWER`); một fork có thể có nhiều PR mở. Thay đổi không lưu: mỗi lần xem tính lại như xem trước merge (giới hạn `sync`), và mỗi thay đổi có `key` ổn định (id node phía nguồn, `collection`, `variable:<key>`). Chỉ người duyệt được Approve/Decline; một Decline đóng PR, không thì một Approve thành `approved`. Merge không cần duyệt: Editor của nguồn merge bằng đúng luồng merge fork và PR thành `merged` trong cùng transaction, nên hai lần merge cùng lúc hay merge sau một Decline đều trả 409 `PULL_REQUEST_CLOSED`. Merge thường không cần mở được fork (fork thường nằm ở workspace cá nhân của tác giả); `mergeAndUpdate` và `mergeAndDelete` tác động lên fork nên vẫn cần Editor ở đó. Duyệt và sửa PR ghi có chốt theo `rev`, đọc lại khi bị người khác ghi trước, nên không đè mất nhau. Mỗi nguồn nhận tối đa 100 PR đang mở (409 `PULL_REQUEST_LIMIT`); sửa PR tính vào giới hạn `comment`, và mỗi người duyệt chỉ được báo mở PR một lần (`notified`). Xem trước của PR tính giới hạn `sync` vào nguồn, không vào fork. Ai mở được nguồn thì xem và bình luận được (404 `PULL_REQUEST_NOT_FOUND` nếu không). Comment của PR dùng module comment, lưu trên nguồn với `pullRequestId` và `changeKey`, không hiện ở panel comment của collection; sửa, xoá, reaction, resolve qua endpoint comment của nguồn. Thông báo `pullRequest.opened` (người duyệt), `reviewed` và `merged` (tác giả); link `?pr=<id>` mở PR trên trang nguồn. Purge nguồn xoá PR vào nó; PR từ fork đã purge ở lại làm lịch sử, không merge được nữa.
- **Giới hạn và an toàn:** `fork` 10/phút mỗi người, 20 mỗi nguồn; xem trước, pull, merge (`sync`) 30/phút mỗi người, 60 mỗi fork. `auth` merge nguyên khối. Merge chỉ đọc thuộc tính riêng của object, nên tên biến như `constructor` không chạm prototype. "Merge and delete" kiểm quyền xoá fork trước khi merge; bước cập nhật hoặc xoá fork sau merge thất bại thì trả `followUp: "failed"` (merge vẫn giữ).

Mọi lý do hỏng trả cùng một lỗi.

## Environments và biến

Module `apps/api/src/modules/environments/`, operation `client.*` (toolset MCP `client`). Kiểu, schema zod và resolver nằm ở `@localman/shared/api-client` (`environments/`). UI ở `apps/web/src/features/environments/`, sau cờ web `environments` (cần cả `workspaces` và `apiClient`).

- **Mô hình:** mỗi biến có định nghĩa (tên, kiểu `default`/`secret`, bật/tắt, mô tả) và **shared value** giống nhau với mọi người xem được; mỗi người còn có **giá trị local** riêng, không đồng bộ. Gửi request và script dùng giá trị local nếu có, không thì shared. Áp cho environment, globals của workspace và biến collection (biến collection vẫn lưu trong gốc collection; chỉ thêm giá trị local).
- **Lưu trữ:** `environments` (workspace, tên, màu, `variables[]` có id ổn định), `global_variables` (một document mỗi workspace, tạo ở lần lưu đầu), `local_variable_values` (một document mỗi người, mỗi scope `environment:<id>`/`collection:<id>`/`global:<workspaceId>`, mỗi tên biến, nên script và bảng không ghi đè nhau), `active_environments` (một document mỗi người mỗi workspace). Giới hạn: 200 environment mỗi workspace (kiểm dưới khoá workspace), 200 biến mỗi scope, 500 giá trị local mỗi người mỗi scope.
- **Secret:** shared value và giá trị local của biến `secret` mã hoá AES-256-GCM bằng `TokenCipher` với keyring `VARIABLE_ENCRYPTION_KEY` (tách khỏi khoá session vì giá trị biến sống vô thời hạn; xoay khoá bằng cách thêm khoá mới lên đầu, giữ mọi khoá cũ). Associated data là slot (`shared:<scope>:<variableId>`, `local:<userId>:<scope>:<key>`), nên giá trị chép sang chỗ khác không mở được. Thiếu keyring thì lưu giá trị secret trả 503 `SECRET_STORAGE_UNAVAILABLE`, phần còn lại vẫn chạy. Biến đổi kiểu thì giá trị local của mọi người được mã hoá lại. Viewer không bao giờ nhận shared value của secret (`sharedHidden: true`); duplicate của Viewer để trống secret đó.
- **Quyền:** environment là phần tử (`ENVIRONMENT_PERMISSIONS`, adapter `environment` cho share, move, request access). Tạo cần `addElements` của workspace; sửa định nghĩa và shared value cần Editor; mọi vai trò đặt giá trị local. Xoá cần Editor trên environment và Admin/Editor của workspace; xoá là vĩnh viễn (có dry run), kéo theo giá trị local, share, access request và lựa chọn active. Globals: thành viên workspace dùng, Admin/Editor sửa shared. Xoá workspace team xoá luôn environment và globals của nó trong cùng transaction.
- **Gửi request (web):** `useVariableLayers` dựng các tầng globals < collection < environment đang active (mỗi tầng đã áp giá trị local, cùng hàm `buildVariableLayers` với highlighter) cho `prepareSend`; biến tạm của tab, rồi `lm.variables` của script đứng trên cùng. Request dùng một secret bị giấu với người gửi (Viewer chưa đặt giá trị local) thì dừng trước khi ra mạng với mã `SECRET_WITHHELD`. Server **không** tự điền secret đó khi proxy: proxy gửi tới URL bất kỳ nên Viewer sẽ đọc được secret qua server riêng; Viewer đặt giá trị local của mình, hoặc xin quyền Editor.
- **Script:** `lm.globals`, `lm.collectionVariables`, `lm.environment` đọc giá trị mỗi scope như khi gửi (local trước, chỉ biến bật, không bao giờ có secret bị giấu); `lm.variables.get` tìm theo thứ tự giá trị của script, environment, collection, globals. `set`, `unset`, `clear` trong pre-request có hiệu lực ngay với `{{name}}` của chính lượt gửi; sau lượt gửi (kể cả khi request lỗi hoặc bị huỷ, như Postman), thay đổi được lưu thành **giá trị local** của người gửi (`set` → local value, `unset`/`clear` → về shared), không bao giờ sửa shared value (`use-script-scope-saver.ts`). Đích lưu (workspace, environment đang active, collection của request) được chốt lúc bắt đầu gửi, nên đổi environment trong lúc chờ response không chuyển thay đổi sang environment mới. Lưu lỗi thì báo; ghi vào scope không có chỗ lưu (không có environment active, request ngoài collection) thì báo riêng. Trong sandbox, mỗi scope lưu được nhận tối đa 700 tên (200 định nghĩa cộng 500 giá trị local), tên 1–200 ký tự không có khoảng trắng đầu/cuối, giá trị tối đa 10 000 ký tự, đúng giới hạn của giá trị local. Request chỉ có script (không dùng `{{name}}`) vẫn gửi được khi không đọc được biến; script khi đó chỉ thấy biến collection của tab đã gắn collection, các scope khác rỗng. Script `set` một biến đang tắt chỉ đổi giá trị local, biến vẫn tắt nên `{{name}}` không lấy giá trị đó (như bảng biến).
- **Biến động:** `$guid`, `$timestamp`, `$isoTimestamp`, `$randomInt`, `$randomUUID` sinh không cần Faker; nhóm `$random*` của Postman (`DYNAMIC_VARIABLES`) map sang hàm trong whitelist Faker (`faker-dynamic-variables.ts`). Web chỉ tải chunk Faker khi lượt gửi có tên như vậy; preview và code snippet giữ nguyên tên như gõ. Tải chunk lỗi thì lượt gửi dừng với `DYNAMIC_VARIABLES_UNAVAILABLE`.
- **Trong editor:** khi cờ bật, biến trong URL, params, headers, auth và body được tô theo loại (đã khai báo, biến động, chưa khai báo); hover hiện giá trị, scope thắng và giá trị bị ghi đè; gõ `{{` hiện gợi ý. "Set as variable" (bôi đen trong request hoặc response) và "Add to" (hover biến chưa khai báo): Editor của scope tạo biến với shared value đó; tên đã có thì cảnh báo trước là thay shared value cho mọi người, giữ nguyên trạng thái bật/tắt, và sau khi ghi shared thành công thì reset giá trị local của người bấm để giá trị mới có hiệu lực. Viewer chỉ đặt được biến tạm. Secret bị giấu với người xem được tô màu cảnh báo, vì lượt gửi dùng nó sẽ dừng với `SECRET_WITHHELD`. Biến tạm sống trong bộ nhớ của từng tab, mất khi đóng tab.
- **Thao tác hàng loạt:** "Reset all" và "Unshare all" là một lần ghi (PATCH local hoặc PUT shared). "Share all" và "Update all shared values" ghi shared trước, chỉ khi thành công mới reset giá trị local đã share, nên lưu shared lỗi không làm mất giá trị local. Không ghi revision. Unshare chỉ xoá shared value.
- **Nơi đang dùng:** `client.listEnvironmentCollections` trả tối đa 100 collection còn sống, cùng workspace, người gọi đọc được, có quan hệ hiệu lực với environment (`linkedEnvironmentId` của Editor thắng, không thì `sharedEnvironmentId`); thanh Info của environment hiện danh sách này, bấm mở được.
- **Import/export:** `client.exportEnvironment` trả file environment của Postman chỉ có shared value (secret luôn rỗng, không có giá trị local); `client.importEnvironment` nhận file đó (kiểu `text`/`any` thành `default`, kiểm trùng tên và giới hạn), quyền như tạo environment, secret được mã hoá như lúc tạo. File sai trả 400 `INVALID_ENVIRONMENT_FILE` kèm `details.issue`.


## Resources và dữ liệu mock

Module `apps/api/src/modules/resources/`, operation `mock.*` dưới `/api/v1/projects/:projectId/resources` (cộng `GET /api/v1/faker-methods`). Zod, whitelist Faker và template nằm ở `packages/shared`, web và api dùng chung. Hằng của resource (`resource-constants.ts`) tách khỏi các module zod (`resource-schema.ts`, `resource-templates.ts` re-export lại), để web đọc qua `@localman/shared/constants` mà không kéo zod và catalog Faker vào trang; catalog chỉ nằm trong chunk modal resource.

- **Resource** (collection `resources`): `projectId`, `parentId` (cây cha–con), `name` (một đoạn path: `^[A-Za-z0-9][\w-]*$`, tối đa 64), `schema[]`, `template` (object template hoặc `null`), `endpoints[]` (đúng 5 endpoint `GET /:res`, `GET /:res/:id`, `POST /:res`, `PUT /:res/:id` dùng chung cho PATCH, `DELETE /:res/:id`, mỗi cái `enabled` và `response`), `count`, `nextId`, `ownerSub`, `quotaSlot`. Unique `(projectId, parentId, name)`: tên chỉ cần khác giữa các anh em. Cây sâu tối đa `MAX_RESOURCE_DEPTH` (10) tầng.
- **Schema:** field `{ name: /^[\w\-.]+$/, type, fakerMethod?, childId? }`, tối đa 50 field, không được tên `__proto__`, `constructor`, `prototype` (cùng danh sách `FORBIDDEN_KEYS` với key JSON). `id` (Object ID) và `{parent}Id` (Parent ID, `parentKeyOf(tên cha)`: `users` → `userId`) là field hệ thống, không nằm trong `schema`; field schema hay key cấp một của object template trùng tên với chúng bị từ chối (giá trị sẽ bị giá trị sinh ra che mất). Đổi tên cha mà bản ghi con đã có key trùng `{parent}Id` mới thì 409 `FIELD_CONFLICT`. `Parent Resource` và `Child Resource` là field quan hệ: không lưu vào record, mock runtime phân giải khi trả lời. Mặc định khi tạo: `createdAt` (`date.past`), `name` (`name.fullName`), `avatar` (`image.avatar`).
- **Record** (collection `records`): `resourceId`, `projectId`, `id` (chuỗi), `parentRecordId`, `data`. `id` và `parentRecordId` là cột riêng, không nằm trong `data`, nên đổi tên hay đổi cha không phải viết lại record; `toRecordView` ghép thành `{ id, {parent}Id, ...data }`. Unique `(resourceId, id)`, index `(resourceId, parentRecordId)`; thứ tự là thứ tự chèn (`_id`).
- **Whitelist Faker** (`faker-method-catalog.ts` cho danh sách id, `faker-methods.ts` cho hàm chạy, import qua `@localman/shared/faker-methods` để web không kéo Faker vào bundle): 249 method theo 21 nhóm, id giữ tên của nguồn (Faker 5: `name.*`, `address.*`, `datatype.*`) và map sang API Faker 10. Mỗi id là một hàm gọi tĩnh; tra cứu bằng `Map`, nên `constructor`, `__proto__` hay `helpers.fake` không gọi được gì. Kết quả luôn là JSON (ngày thành chuỗi ISO). Faker 10 bỏ LoremFlickr, nên các id ảnh theo chủ đề của nguồn (`image.cats`, `image.urlLoremFlickr`…) trả URL ảnh chung.
- **JSON template** (`json-template.ts`): chỉ thay khi **cả chuỗi** là một biến: `"$mockData"`, `"$count"` (chỉ trong custom response) hoặc `"$category.method"`. Chuỗi dài hơn như `"Giá $5"` giữ nguyên. Lúc lưu, tham chiếu lạ bị 400 (bắt lỗi gõ như `$mockdata` và `$constructor.constructor`); lúc render, tham chiếu lạ giữ nguyên chữ, không bao giờ chạy. Object được dựng lại bằng `Object.fromEntries` nên key `__proto__` không chạm prototype; key `__proto__`, `constructor`, `prototype` bị từ chối ở đầu vào (mongoose âm thầm bỏ `__proto__`). Giới hạn lúc lưu: template sâu 10, 2.000 giá trị, tối đa `MAX_METHOD_REFERENCES` (200) lời gọi Faker. Lúc render (`json-template-render.ts`) đầu ra được đo **trong khi** sinh, theo số giá trị (50.000) và theo byte (`maxBytes`, ước lượng JSON gọn); vượt là dừng ngay với `TEMPLATE_TOO_LARGE`, nên template quá lớn chỉ tốn tối đa một ngân sách công sức.
- **Sinh dữ liệu:** `POST …/:resourceId/generate { count: 0..100 }` thay toàn bộ dữ liệu (0 là reset), id lại từ "1". Field Faker gọi whitelist, `String` ra `"<tên> <số thứ tự>"`, `Number` ra số thứ tự, `Boolean` ngẫu nhiên, `Object` `{}`, `Array` `[]`, `Date` một ngày trong quá khứ (giống nguồn). Có `template` thì dùng template thay schema. Resource con chia ngẫu nhiên N bản ghi cho các bản ghi cha; cha chưa có dữ liệu thì 409 `PARENT_HAS_NO_DATA` (message tiếng Anh, client dịch theo mã). `generate_all` vẫn nguyên tử (một transaction) nhưng sinh và chèn **từng resource** theo thứ tự cha trước con, nên bộ nhớ chỉ giữ dữ liệu của một resource (`count` tuỳ chọn; không có thì giữ số hiện tại, resource rỗng nhận 10 như prototype). `reset_all` xoá mọi bản ghi, giữ schema.
- **Sửa dữ liệu thô:** `PUT …/:resourceId/data { data: [...] }` (registry chỉ nhận body là object, nên mảng nằm trong `data`; riêng route này nhận body tới 2,5 MB, các route khác giữ 100 KB), tối đa `MAX_RECORDS_PER_RESOURCE` (1000, cũng là trần POST của mock runtime; generator dừng ở `MAX_GENERATE_COUNT` = 100) object. `id` tuỳ chọn, duy nhất, là số nguyên không âm hoặc chuỗi an toàn cho URL có ít nhất một chữ hoặc số (chặn `.`, `..`); thiếu thì đánh số tiếp sau id số lớn nhất không quá 10^9. Với resource con, `{parent}Id` phải trỏ tới bản ghi cha có thật (`null` bị từ chối), thiếu thì gán ngẫu nhiên. Lỗi JSON trả đúng `path` của giá trị hỏng.
- **Giới hạn thao tác nặng:** generate và `generate_all` (chung bộ đếm), `reset_all`, `PUT …/data` và clone project đếm theo tài khoản và theo project trong `rate_limit_windows` (`heavyOperationRateLimit` trong `config/runtime-settings.ts`, `lib/operation-rate-limit.ts`), kiểm sau bước phân quyền nên người không có quyền không tiêu được ngân sách của project. Bộ đếm tài khoản kiểm trước; tài khoản đã vượt mức thì dừng ở đó, không lấy thêm lượt của project, nên một thành viên spam không khoá các thành viên khác. Mặc định mỗi phút: generate 30 mỗi tài khoản, 60 mỗi project; `PUT …/data` 60 và 120; `reset_all` 30 và 60; clone 10 và 20 (theo project nguồn); `import_resources` 60 và 120 (tính cả dry run, vì preview cũng đọc tới 2 MB nguồn); `suggest_faker_methods` 120 mỗi tài khoản (không thuộc project). Dry run của generate, reset và clone không bị tính; dry run của `PUT …/data` bị tính vì vẫn đọc và kiểm cả body. Vượt thì 429 `RATE_LIMITED`; web hiện câu tiếng Việt chung ("Bạn thao tác quá nhanh…", `errorMessage` trong `lib/api-client.ts`).
- **Trần kích thước** (`MAX_RECORD_BYTES` 32 KB mỗi record, `MAX_RESOURCE_BYTES` 2 MB mỗi resource, trong `plan-limits.ts`, áp cho mọi gói): kiểm khi sinh (template dừng sớm theo byte, tổng đo dần), khi `PUT data`, trong `writeRecords` và khi clone; mỗi resource lưu tổng hiện tại ở `dataBytes` (đặt lại ở mọi đường ghi: sinh, `PUT data`, `generate_all`, `reset_all`, clone, reset cây con; resource cũ chưa có trường này được đo lại một lần ở lượt ghi mock kế tiếp); vượt thì 413 `DATA_TOO_LARGE` với `details: { limit: "record" | "resource", maxBytes, actualBytes, resourceId, name }` (`actualBytes` là ước lượng; `generate_all` cũng nêu resource gây lỗi). Lúc lưu, object template được ước lượng record xấu nhất từ bảng trần kích thước từng method Faker (`faker-method-sizes.ts`, đo hàng nghìn lần rồi nhân đôi; test đo lại để bắt khi nâng Faker) cộng phần chữ cố định; vượt 32 KB thì 400 `TEMPLATE_TOO_LARGE` (`details: { maxBytes, estimatedBytes }`).
- **Nhất quán cha–con** (chi tiết ở [ADR-0001](decisions/0001-resource-data-in-project-transactions.md)): mọi thao tác ghi resource hoặc record của dashboard chạy trong transaction Mongo, giữ khoá cây của project rồi kiểm project còn tồn tại và không có `deletingAt` (không thì 404). Sau khi dữ liệu cha bị thay, bản ghi con trỏ tới id cha còn tồn tại được giữ, bản ghi con mồ côi được gán ngẫu nhiên một bản ghi cha mới; cha rỗng thì cả cây con bị reset. Đổi cha (`PUT …/:resourceId/parent`) reset dữ liệu của resource đó và mọi resource dưới nó, bỏ field quan hệ không còn hợp lệ. Xoá resource xoá cả cây con và record, và bỏ field `Child Resource` trỏ tới nó.
- **Import, xuất type, gợi ý Faker** (toolset `mock-advanced`, `modules/resources/mock-advanced-operations.ts`): `POST …/resources/import` (`import_resources`) suy cây resource từ JSON mẫu, CSV hoặc một schema OpenAPI 3 (`inferSchema` của `packages/shared/src/schema-inference.ts`, input ≤ 2 MB, body request tới 4,5 MB để chuỗi nguồn sau JSON-escape vẫn vừa; không bao giờ tải `$ref` ngoài; OpenAPI đọc tài liệu một lần, mọi component dùng chung một walker và ngân sách `MAX_OPENAPI_IMPORT_STEPS`, thử tối đa `MAX_COMPONENTS_TRIED` component) rồi tạo cả cây trong **một** transaction project, tính vào hạn mức resource của chủ project: list lồng trong nguồn thành resource con kèm field `Child Resource`, bản ghi mẫu (JSON/CSV, tối đa 1.000 mỗi resource) seed qua `prepareRecords`; `?dryRun=true` chỉ xem trước (field, 5 bản ghi, `resourcesLeft`). Lỗi nguồn là `SCHEMA_IMPORT_FAILED` với `details: { reason, ...params }`, cảnh báo có `code` + `params` để web dịch (`schema-import-errors.ts`); `create_resource_from_schema` dùng chung service tạo (`resource-import-service.ts`) và cùng dạng lỗi. `POST /projects/:projectId/resource-types` (`export_resource_types`) trả mã TypeScript hoặc Zod (`type-exporters.ts`, web cũng chạy hàm này phía client); `POST /faker-methods/suggestions` (`suggest_faker_methods`) gợi ý method theo tên field (`faker-field-matcher.ts`).
- **Chaos và rules** lưu trên endpoint qua `PUT …/:resourceId` (kiểm bằng `endpointInputSchema`), view trả `endpoints[].chaos`/`rules` và `revision` (tăng mỗi lần lưu; khoá bộ đếm `nth` của mock runtime, xem [api-contract](api-contract.md#rules-và-chaos)).
- **Hạn mức resource:** `limitsFor(plan).resources` tính trên **mọi resource của mọi project user sở hữu** (tên field không có hậu tố `Per…` như `membersPerWorkspace`), không tính project được chia sẻ. Resource bị tính cho chủ project (`ownerSub`). Chống race giống project: unique `(ownerSub, quotaSlot)`, slot trống nhỏ nhất (`billing/quota-slots.ts`). Clone project tính toàn bộ resource của bản sao vào hạn mức người clone; vượt thì 403 `PLAN_LIMIT_REACHED` (`limit: "resources"`) và bản clone bị xoá. Custom response và object template mở cho mọi gói.
- **Phân quyền:** đọc cần `can(read)`, ghi cần `can(editResources)` của project (owner và collaborator đã accept); không đọc được project thì 404, resource không thuộc project cũng 404. Thao tác xoá hoặc thay dữ liệu (`delete`, `parent`, `generate`, `generate_all`, `reset_all`, `PUT data`) là destructive và nhận `?dryRun=true` để xem trước danh sách `changes` (`countBefore` → `countAfter`).
- **Project dependents:** `resources` (đếm resource; xoá resource, record và khoá cây; clone chép cả cây, schema, template, endpoint và record trong một transaction giữ cả khoá project nguồn, nên đọc một snapshot nhất quán và chép record từng resource; map id resource cũ sang mới, giữ `id` và `parentRecordId` của record) và `records` (chỉ đếm và xoá).
- **Ghi chú cho mock runtime:** key bắt đầu bằng `$` hoặc chứa `.` hợp lệ trong dữ liệu và luôn nằm dưới `data`; không bao giờ dựng đường dẫn filter hay update Mongo từ key dữ liệu (lọc, sắp xếp, merge làm trong bộ nhớ hoặc thay cả `data`). Tên resource anh em phân biệt hoa thường (`Side` và `side` cùng tồn tại được), nên router mock phải so khớp tên phân biệt hoa thường. Cách runtime giữ các điều này: xem mục Mock runtime.

## Mock runtime

Module `apps/api/src/modules/mock-runtime/`, gắn vào app cổng 4100 (`mock-server.ts`). Đây là API công khai do người dùng định nghĩa nên không đi qua operation registry. Mỗi project còn có MCP endpoint `{prefix}/mcp` (Hosted Mock MCP, mục bên dưới); MCP để quản lý project và resource là các operation `mock.*` của dashboard.

- **Địa chỉ:** secret lấy từ Host `{secret}.{MOCK_BASE_DOMAIN}` (không phân biệt hoa thường như DNS, bỏ cổng, phải là một nhãn DNS hợp lệ), không có thì từ path `/m/{secret}/…` (dùng khi chưa có wildcard TLS hoặc ở local). Sau đó bỏ `prefix` của project (so khớp phân biệt hoa thường). Request không trỏ tới project nào (`/healthz` trên host trần) đi tiếp xuống `/healthz` và 404 chung; trên host của project, `/healthz` là một route mock bình thường.
- **Cache project:** `secret → { id, prefix, owner, plan đã lưu của owner }` trong LRU 10.000 mục, TTL 60 giây, cả secret không tồn tại (lượt dò secret ngẫu nhiên tốn một truy vấn rồi trúng cache có giới hạn). Dashboard chạy cùng process nên đổi prefix hoặc bắt đầu xoá project (tombstone `deletingAt`) xoá mục cache ngay. Thay đổi khác (plan đổi bằng CLI `set-user-plan`) có hiệu lực trễ tối đa 60 giây; ngày hết hạn Pro vẫn được so mỗi request. Cây resource (schema, endpoint) đọc lại mỗi request (một truy vấn theo `projectId`), nên sửa ở dashboard có hiệu lực ngay.
- **Route:** tự tách path thành `[res, id?, childRes, id?, …]` theo cây, độ sâu tuỳ ý, tên so khớp phân biệt hoa thường (không dùng route Express theo tên). Đoạn đầu khớp resource gốc cùng tên, nếu không có thì khớp resource lồng duy nhất mang tên đó (route phẳng `/:child` của nguồn); tên trùng ở nhiều nhánh mà không có gốc thì 404. Route lồng kiểm từng bản ghi tổ tiên tồn tại và đúng cha (`/users/2/posts/1` là 404 nếu post 1 thuộc user khác) và lọc theo `parentRecordId`; route phẳng trả mọi bản ghi.
- **Endpoint:** GET list, GET one (và HEAD), POST, PUT/PATCH (dùng chung endpoint PUT), DELETE. Endpoint tắt, method khác hoặc kết hợp sai (POST lên `/:res/:id`) trả 404. Không tìm thấy project, resource hay bản ghi đều trả 404 với body là chuỗi JSON `"Not found"` như nguồn; các lỗi khác theo dạng `{ error: { code, message } }`.
- **Query (trong bộ nhớ):** tải bản ghi của collection bằng truy vấn cố định trên cột hệ thống (`resourceId`, `parentRecordId`) rồi lọc, sắp xếp, phân trang trong JS trên view của bản ghi. `search`/`filter`: chuỗi con không phân biệt hoa thường trên mọi giá trị chuỗi cấp một (kể cả `id`). `<field>=v` chỉ với field của schema (hoặc key cấp một của object template) và `id`, `{parent}Id`, kết hợp AND; giá trị được ép theo kiểu của giá trị trong bản ghi: chuỗi khớp chuỗi con không phân biệt hoa thường, số và boolean khớp đúng (`completed=false`), `null` khớp chữ `null`, object và mảng không khớp; `id` và `{parent}Id` khớp nguyên chuỗi. Key không phải field bị bỏ qua. `page`/`p`, `limit`/`l` (số nguyên dương; không có `limit` thì trả hết, lớn hơn 100 thì hạ về 100, giá trị hỏng bị bỏ qua). `sortBy`/`sortby`/`orderBy`/`orderby` với field có thật (số và chuỗi số so theo số, nên id "2" trước "10"), `order=desc` (không phân biệt hoa thường), mặc định asc, sort ổn định; field lạ bị bỏ qua. Key bắt đầu bằng `$`, chứa `.`, `[` hoặc `]` (parser "simple" của Express giữ nguyên `title[$ne]` thành tên key), là `__proto__`/`constructor`/`prototype`, giá trị lặp (`a=1&a=2`) và `sortBy` mang tên như vậy đều trả 400 `INVALID_QUERY` trước khi chạm DB. Mọi lượt đọc field dùng `Object.hasOwn`. Field có tên chứa `.` vì thế không lọc được qua query.
- **Ghi:** body là object JSON (thiếu body là `{}`), qua `checkJson` (giới hạn JSON chung, key `FORBIDDEN_KEYS` ở mọi tầng bị 400 `VALIDATION_ERROR`) và được dựng lại từ thuộc tính riêng, nên `{"__proto__":…}` hay `constructor.prototype` không chạm prototype. `id`, `{parent}Id` và tên field quan hệ bị bỏ khỏi dữ liệu. Mọi lượt ghi chạy trong `inProjectTransaction` (khoá project, project bị tombstone thì 404) và ghi bằng driver gốc với cả `data`, nên key `$x`, `a.b` được lưu đúng như dữ liệu, không bao giờ thành toán tử hay đường dẫn.
  - POST: `id = nextId` (bỏ qua id đã có từ dữ liệu dán tay), rồi `nextId + 1`, `count + 1`; field schema (hoặc key template) mà body thiếu được sinh như generator (`FILL_MISSING_FIELDS_ON_CREATE` ở `crud-handlers.ts`), trả 201. Route lồng gán `{parent}Id` theo path (giá trị trong body bị bỏ qua); route phẳng của resource con cần `{parent}Id` trỏ tới bản ghi cha có thật, thiếu hoặc sai là 400.
  - PUT/PATCH: merge body vào dữ liệu (key cũ giữ thứ tự), không đổi `id` hay `{parent}Id`, trả 200.
  - DELETE: trả bản ghi đã xoá (quan hệ phân giải trước khi xoá), xoá dây chuyền bản ghi con theo từng tầng và giảm `count` tương ứng.
  - Trần: `MAX_RECORDS_PER_RESOURCE` (1000) → 409 `RECORD_LIMIT_REACHED`; `MAX_RECORD_BYTES`/`MAX_RESOURCE_BYTES` đo như dashboard → 413 `DATA_TOO_LARGE`; body quá 100 KB → 413 `PAYLOAD_TOO_LARGE`. Trần resource được kiểm **theo delta** trên `dataBytes` của resource (tổng cũ − bản ghi cũ + bản ghi mới), không đọc các bản ghi khác; POST/PUT/PATCH/DELETE và xoá dây chuyền cập nhật `dataBytes` trong cùng transaction.
- **Field quan hệ:** `Parent Resource` nhúng bản ghi cha (một tầng, không phân giải tiếp quan hệ của nó, `null` nếu thiếu); `Child Resource` là mảng bản ghi của resource con trực tiếp thuộc bản ghi này. Phân giải sau khi lọc và phân trang, một truy vấn mỗi nguồn (bản ghi cha, hoặc từng resource con) cho cả trang. Lúc lưu, schema chỉ nhận một field `Parent Resource` và một field `Child Resource` cho mỗi resource con (400 `VALIDATION_ERROR` ở đúng field, web báo ngay ở ô đó; `relationSourceOf` trong `@localman/shared`). Trước khi nạp, `relation-budget.ts` cộng số byte của trang với `dataBytes` của các nguồn (nhân số field dùng nguồn đó, cho schema cũ còn field trùng; resource chưa đo tính như đầy 2 MB). Vừa trần response thì nạp song song; vượt thì đọc tuần tự bằng cursor, trừ dần ngân sách theo từng bản ghi và dừng ngay bằng 422 `RESPONSE_TOO_LARGE` khi hết, nên bộ nhớ không vượt quá cỡ trần dù nguồn lớn, còn trang có ít bản ghi con vẫn trả được.
- **Response:** template `$mockData` mặc định trả thẳng dữ liệu; template khác render qua `json-template` với `$mockData`, `$count` và `$category.method` (Faker chạy mỗi request, tham chiếu lạ giữ nguyên chữ, không bao giờ chạy). `$count` của list là số bản ghi sau lọc, trước phân trang; ở endpoint khác là số bản ghi của collection theo route (chỉ đếm khi template dùng `$count`). Response được đo trước khi gửi (object dùng chung như bản ghi cha chỉ duyệt một lần) và khi render; quá `MAX_RESOURCE_BYTES` (2 MB) thì 422 `RESPONSE_TOO_LARGE` (gợi ý dùng `?limit`). Số byte đo được cộng vào ngân sách byte của secret; list tính số lớn hơn giữa byte gửi đi và byte collection đã đọc (route phẳng dùng `dataBytes`, route lồng đo các bản ghi đọc được), nên một lượt lọc không ra kết quả vẫn tốn ngân sách bằng phần đã quét.
- **Rate limit:** cửa sổ cố định 1 giây trong bộ nhớ process, kiểm theo thứ tự và chạy trước khi đọc body; vượt bất kỳ mức nào thì 429 `RATE_LIMITED` kèm `Retry-After`. Preflight không bị tính.
  - `MOCK_RATE_LIMIT_PER_IP`: mặc định 30 request/s, IP theo `TRUST_PROXY`, IPv6 gộp /64.
  - `MOCK_RATE_LIMIT_PER_SECRET`: mặc định 60 request/s.
  - `MOCK_WRITE_RATE_LIMIT_PER_SECRET`: mặc định 10 lượt POST/PUT/PATCH/DELETE mỗi giây, vì mỗi lượt ghi giữ khoá project trong một transaction.
  - `MOCK_RESPONSE_BYTES_PER_SECOND`: mặc định 20 MiB body phản hồi mỗi secret mỗi giây. Request bị từ chối khi giây hiện tại đã tiêu hết ngân sách; response bắt đầu trong ngân sách được gửi trọn, nên một giây có thể vượt tối đa một response (2 MB).
  - Chỉ chính xác khi mock runtime chạy một process (PM2 fork); nhiều process thì mỗi process cho đủ mức.
  - Mock runtime đang chạy chung process với dashboard API. Khi tải mock tăng, nên tách nó thành process PM2 riêng (cùng code, chỉ mở cổng 4100) để CPU dùng cho render và đo JSON không làm chậm dashboard; khi đó cache project không còn được dashboard xoá trực tiếp, nên đổi prefix hoặc xoá project có độ trễ tới TTL 60 giây (chưa làm).
- **Hạn mức tháng:** theo **chủ project**, `limitsFor(plan hiệu lực).mockRequestsPerMonth` (Pro hết hạn tính như Free; `null` là không giới hạn). `UsageMeter` đọc tổng tháng (giờ Saigon) của owner một lần, đếm trong bộ nhớ và `$inc` vào `usage_counters` mỗi 5 giây và khi shutdown (trước khi ngắt Mongo). Request đã qua rate limit và trỏ tới project có thật đều được tính (kể cả 404 trong project); request bị từ chối thì không. Hết hạn mức thì 429 `MONTHLY_QUOTA_EXCEEDED`. Request được nhận cũng được đếm theo project trong bộ nhớ (`project-activity.ts`) và ghi cùng nhịp 5 giây bằng một `bulkWrite` (`$inc mockRequests`, `$max lastRequestAt`), không ghi Mongo trên mỗi request. Khi một lượt `$inc` đưa tổng vượt 80% hoặc 100%, chủ project nhận thông báo `usage.quota` (link `/account`); mỗi lượt `$inc` phủ một khoảng đếm riêng nên mỗi ngưỡng chỉ báo một lần mỗi tháng, kể cả khi nhiều process. Nhiều process thì mỗi process có thể vượt hạn mức tối đa một chu kỳ flush.
- **HTTP:** `Access-Control-Allow-Origin: *` (không bao giờ kèm credentials), preflight trả 204 với các method mock và đúng danh sách header được hỏi (nên `Authorization` dùng được), `Max-Age` 600. Mọi response có `X-Localman-Request-Id` (xem Log request); body là `application/json`. Helmet mặc định trừ `Cross-Origin-Resource-Policy: cross-origin`, `X-Frame-Options: DENY` và CSP: CSP của helmet được thay bằng đúng một header `Content-Security-Policy: sandbox; default-src 'none'; frame-ancestors 'none'` (`MOCK_CONTENT_SECURITY_POLICY` trong `mock-server.ts`) kèm `X-Content-Type-Options: nosniff`, đặt trước mọi middleware khác nên có trên mọi response (mock, rule, upstream, inbox, preflight, lỗi, 404). Lý do: `/m/` cùng origin với dashboard, còn upstream và inbox trả nội dung do người khác quyết; `sandbox` cho tài liệu một origin mờ (không script, không cookie của dashboard). nginx lặp lại cùng header ở `location /m/` làm lớp dự phòng. Lỗi không lường trước trả 500 `INTERNAL_ERROR` không chi tiết; log chỉ ghi method, 4 ký tự đầu của secret (path có thể chứa secret) và request id (giữ ở `res.locals`, trùng header client nhận), không ghi body.
- **Hosted Mock MCP** (`apps/api/src/modules/mcp/mock-mcp-server.ts`, hợp đồng ở [api-contract.md, mục MCP](api-contract.md#mcp)): middleware mount trước router REST. Path có đoạn cuối `mcp` được rate limit như lượt đọc (chưa biết prefix trước khi resolve project); sau khi resolve, chỉ đúng `{prefix}/mcp` mới là MCP, còn lại trả về REST (REST ghi trên path như vậy lấy bù lượt ghi). Mỗi request: kiểm Bearer token tuỳ chọn (`mcp_tokens`, một truy vấn), đọc cây resource, lấy tool từ cache theo secret + revision cây (`mock-mcp-tools-cache.ts`), dựng `McpServer` mới và phục vụ qua `createMcpHandler` của SDK với body đã được `express.json` đọc (`mcp-express-bridge.ts`). Body là mảng (JSON-RPC batch) bị 400 ở bridge, `subscriptions/listen` bị từ chối (`mock-mcp-guards.ts`). Tool call (`mock-tool-call.ts`) được xét lại rate limit theo IP, secret, byte (và lượt ghi với tool ghi), tính hạn mức tháng (`admitMonthly`, cùng `UsageMeter` và `ProjectActivity`), dựng `MockTarget` từ `parentId` bằng cách đi ngược `parentRecordId`, rồi gọi `runEndpoint` như REST; kết quả không qua custom response.
- **Mock lai (upstream)** (`upstream-*.ts`, `mock-route-call.ts`): project có thể có `upstream` (`tunnel` + `port`, hoặc `url` + `baseUrl`; không có là `none`), chỉ owner đặt qua `traffic.setProjectUpstream` (không có MCP tool vì đổi nơi credential của người gọi đi tới). Request có path khớp resource và method có endpoint đang bật thì mock trả; còn lại (ngoài prefix, resource lạ, method không có endpoint) được chuyển sang upstream tới `{gốc upstream}{path dưới secret, gồm prefix}?{query}`. `tunnel:<port>` tra ánh xạ thủ công `localhost:<port>` đang bật của **owner** trong `client_settings.tunnelMappings`, URL phải còn thuộc `TUNNEL_DOMAINS`; `url` chỉ nhận `https://host[:port][/path]` không userinfo, query, fragment, không phải host mock, và host phải qua bộ chặn SSRF ngay lúc đặt (400 `UPSTREAM_URL_BLOCKED`/`UPSTREAM_DNS_FAILED`). Path dưới secret phải không leo ra khỏi điểm đầu khi đọc như một upstream dễ dãi (giải mã percent, `\` là `/`, `.`/`..` được tính; `%2e%2e`, `..%2f`, `%5c`) và URL sau khi ghép phải còn dưới path của `baseUrl`, không thì 400 `UPSTREAM_PATH_INVALID`. Gửi đi bằng `forwardHttpRequest` (`upstream-forwarder.ts`): dùng lại `sendChecked` của proxy (ghim DNS, chặn SSRF với miễn trừ host mock và host tunnel, `X-Localman-Proxy: 1`), không theo redirect, một deadline 25 s (dưới `proxy_read_timeout 30s` của nginx, để client nhận 502 JSON thay vì 504 HTML), đọc response tối đa 2 MB sau giải nén. Header gửi đi là header của client trừ hop-by-hop, `Host` và header hạ tầng (`X-Forwarded-*`, `Forwarded`, `X-Real-IP`, `CF-*`, `X-Localman-*`), `Cookie` bỏ cookie của Localman (`lm_*`, mọi `__Host-*`, vì trình duyệt gửi `__Host-lm_session` tới `/m/`), cộng `X-Forwarded-For` là IP client và `X-Localman-Hop: 1`; body là đúng byte client gửi (JSON giữ bản thô qua `verify` của parser, body khác đọc từ stream), tối đa 100 KB. Response giữ status; header theo **allowlist** (`upstream-response-headers.ts`): `Content-Type`, `Cache-Control`, `ETag`, `Last-Modified`, `Expires`, `Vary` (bỏ `Cookie`), `Content-Language`, `Location`, `Retry-After` và `X-*` trừ `X-Localman-*`, `X-Accel-*` (nginx làm theo), `X-Forwarded-*`, `X-Frame-Options`, `X-XSS-Protection`, `X-Content-Type-Options`. Mọi header khác bị bỏ, nhất là `Set-Cookie`, `Content-Security-Policy*`, `Access-Control-*` (CORS của runtime giữ quyền), `Strict-Transport-Security`, `Content-Disposition`, `Refresh`, `Link`. `Location` tương đối giữ nguyên; tuyệt đối (kể cả `//host`, `/\host`) chỉ giữ khi cùng origin với upstream và được viết lại thành path, khác origin thì bỏ. Mọi response của project có `X-Localman-Source: mock|upstream` (đã thêm vào `Access-Control-Expose-Headers`). Upstream được tính hạn mức tháng như mọi request và tốn ngân sách byte của secret. Lỗi theo dạng của runtime, thêm `hint` cho tunnel: 502 `{ error: { code: "UPSTREAM_UNAVAILABLE", message, hint: "tunelo http <port>", details: { cause, port } } }` với `cause` là `no_tunnel`, `connect`, `timeout`, `dns` hoặc `blocked`; với upstream `tunnel`, câu trả lời do chính Tunelo sinh khi app không tới được (502/504 `text/plain` không charset, body `Tunnel not found: <label>`, `Bad Gateway`, `Gateway Timeout`, `Local service unavailable|timeout`, `Local response error|aborted` hoặc lỗi Node như `read ECONNRESET`; `upstream-tunelo.ts`) cũng thành lỗi này (`connect`/`timeout`), còn 502 của chính app dev được relay nguyên; 502 `UPSTREAM_RESPONSE_TOO_LARGE`; 503 `UPSTREAM_BUSY` (quá 8 request đang chờ upstream của một **owner**, gộp mọi project của họ, hoặc 64 cả process); 508 `UPSTREAM_LOOP` khi request mang `X-Localman-Hop` (vòng lặp qua upstream). Message theo `locale` của owner.
- **Log request** (`request-log-*.ts`, collection `request_logs`): mọi request đã được tính hạn mức của project (REST, không gồm MCP) được ghi một dòng khi response gửi xong: thời gian, method, path thô dưới secret, query, status, ms, `source` (`mock`, `rule` khi rule/chaos trả lời, `upstream`; `inbox`, `callback` dành cho webhook inbox và mock callback), header và body của request (không gồm header hạ tầng) và response. ## Proxy của API client

API client gửi thẳng từ trình duyệt khi được; request phải qua server (header trình duyệt cấm, CORS chặn, user chọn Proxy, tool MCP `send_request`) đi qua operation `client.sendRequest` (`POST /api/v1/proxy`, toolset `client`, code ở `apps/api/src/modules/api-client/proxy-*.ts` và `ssrf-guard*.ts`). Envelope vào/ra là `proxyRequestSchema`/`proxyResponseSchema` của `@localman/shared/api-client`.

- **Dựng request** (`proxy-hop.ts`): `node:http`/`node:https`, mỗi hop một kết nối mới (`agent: false`). Header gửi đi là mảng raw nên giữ thứ tự, chữ hoa thường và header trùng tên; Node không tự thêm `Host`. Header chỉ lấy từ envelope, nên cookie phiên và `Authorization` của request gửi lên Localman không bao giờ tới đích. Bỏ hop-by-hop (RFC 9110 §7.6.1 và mọi tên liệt kê trong `Connection`) và `Content-Length` của user (proxy tự đặt theo body thật; POST/PUT/PATCH không body gửi `0`). `Host` đứng đầu: giá trị user ghi đè nếu có, không thì theo URL (host mock luôn theo URL, xem dưới). Mọi request proxy luôn mang `X-Localman-Proxy: 1` ở cuối: header cùng tên của user bị bỏ, user không xoá hay đổi được.
- **IP của client** (`proxy-headers.ts`, bật theo `options.sendClientIp`): lấy từ `ctx.clientIp` (Express `req.ip`, chỉ tin `X-Forwarded-For` từ `TRUST_PROXY`), `::ffff:` được bỏ. `X-Forwarded-For` và `Forwarded: for=…;proto=<scheme của PUBLIC_URL>` là danh sách nên được nối thêm vào header cùng tên của user; `X-Real-IP` chỉ đặt khi user chưa ghi.
- **Chống SSRF** (`ssrf-guard.ts`, `ssrf-guard-ranges.ts`): mỗi hop resolve DNS (`dns.lookup`, tính cả `/etc/hosts`) lấy **mọi** địa chỉ, một địa chỉ bị chặn là từ chối cả host (chống DNS rebinding một-public-một-private), rồi ghim địa chỉ đầu: `lookup` của socket luôn trả đúng địa chỉ đã kiểm, TLS dùng `servername` theo tên host. IP literal (mọi cách viết, URL parser đã chuẩn hoá `2130706433`, `0x7f.1`) được kiểm không qua DNS. Dải bị chặn: `0.0.0.0/8`, RFC 1918, CGNAT `100.64.0.0/10`, loopback, link-local (metadata `169.254.169.254`), `192.0.0.0/24`, TEST-NET, `198.18.0.0/15`, multicast, `240.0.0.0/4`; IPv6 `::/96`, IPv4-mapped `::ffff:0:0/96`, NAT64 `64:ff9b::/96` và `64:ff9b:1::/48`, `100::/64`, `2001::/23` (Teredo…), `2001:db8::/32`, 6to4 `2002::/16`, ULA `fc00::/7`, link-local, site-local, multicast; cộng **địa chỉ của chính server**: mọi địa chỉ trên network interface của máy (`os.networkInterfaces()`, đọc lại mỗi request, không cần cấu hình) và `PROXY_BLOCKED_CIDRS` (IP công khai không nằm trên interface, ví dụ sau NAT). Mọi phép so host (host mock, host tunnel, và kiểm host mock lúc lưu upstream/callback trong `upstream-config.ts`) dùng `normalizeHostname`: chữ thường, bỏ mọi dấu `.` cuối, nên `abc.{MOCK_BASE_DOMAIN}.` cũng là host mock. Ngoại lệ thứ nhất là **host mock** (`*.{MOCK_BASE_DOMAIN}`, không gồm chính `MOCK_BASE_DOMAIN`, vì apex là dashboard sau Cloudflare): ở cổng mặc định (80/443) nó được tới địa chỉ của server, vì mock runtime chạy ở đó, nhưng `Host` bị ép bằng host của URL và SNI là host đó, nên nginx chỉ chuyển nó vào server block mock (`127.0.0.1:4100`). Dải private/loopback vẫn chặn với host mock; host mock ở cổng khác bị chặn như thường; redirect từ host mock sang host khác được kiểm lại từ đầu. Ngoại lệ thứ hai là **host tunnel**: `https://<label>.<domain>` với `domain` thuộc `TUNNEL_DOMAINS` (mặc định rỗng), `label` đúng một cấp theo regex subdomain của Tunelo, cổng 443. Tunelo chạy cùng IP với server (`*.tunnel.inetdev.io.vn` trỏ `103.72.98.65`), nên host tunnel cũng được tới địa chỉ của server, `Host` bị ép theo URL như host mock và vẫn mang `X-Localman-Proxy`. http, cổng khác, apex hay nhiều cấp subdomain bị chặn như thường; dải private/metadata luôn bị chặn. Cổng tuỳ ý trừ SMTP 25, 465, 587 (body proxy có thể chứa lệnh SMTP, làm IP server bị đưa vào danh sách spam). Lỗi: 403 `PROXY_TARGET_BLOCKED` (`details.reason`: `address`/`port`), không lộ địa chỉ đã resolve. `PROXY_DNS_FAILED` (502) vẫn tách khỏi `PROXY_TARGET_BLOCKED` dù cho người gọi biết một tên nội bộ có resolve được hay không: resolver của server là DNS công khai, tên chỉ có trong `/etc/hosts` không có gì để lộ ngoài sự tồn tại, còn user cần phân biệt "gõ sai host" với "host private" để biết phải dùng Tunelo. Test truyền resolver và địa chỉ cho phép qua `createSsrfGuard`/`createProxyOperations`; không có biến môi trường nào mở được.
- **Redirect** (`proxy-forwarder.ts`): tự xử lý, tối đa 10 khi `followRedirects` (vượt thì 502 `PROXY_TOO_MANY_REDIRECTS`), tắt thì trả chính response 3xx. Mỗi hop kiểm SSRF lại. 303 (và 301/302 sau POST) thành GET, bỏ body và header nội dung; sang origin khác thì bỏ `Authorization`, `Cookie` và `Host` ghi đè. `Location` không phải http(s) thì trả response 3xx.
- **Giới hạn:** body envelope 15 MiB (`bodyLimit`, guest bị 401 trước khi đọc body), body request 10 MB (schema), một deadline `timeoutMs` (mặc định 30 s, tối đa 120 s) cho cả DNS, các hop và đọc body (504 `PROXY_TIMEOUT`). Response đọc tối đa 10 MB **sau giải nén** (gzip, deflate, br; bomb nén bị cắt ở 10 MB), quá thì cắt và `truncated: true`; giải nén lỗi thì trả byte thô. Body là UTF-8 hợp lệ thì trả text (cắt giữa ký tự thì bỏ ký tự dở), không thì base64. Header response giữ thứ tự và trùng tên (`Set-Cookie` chỉ để hiển thị). Timing của hop cuối: `dns` (null với IP literal), `connect`, `tls` (null với http), `ttfb` tính từ đầu hop; `total` tính cả redirect. Lỗi kết nối: 502 `PROXY_CONNECTION_FAILED` với `details.cause` là mã lỗi Node (`ECONNREFUSED`, `CERT_HAS_EXPIRED`…); DNS lỗi: 502 `PROXY_DNS_FAILED`. Giải nén chỉ giữ một buffer lớn: byte thô chỉ giữ tối đa 64 KiB đầu cho tới khi bộ giải nén ra byte đầu tiên; giải nén lỗi ngay từ đầu thì trả byte thô (đọc tiếp tới 10 MB nếu lỗi nằm trong 64 KiB đầu), lỗi giữa chừng thì trả phần đã giải nén với `truncated: true`.
- **Đồng thời và huỷ** (`proxy-concurrency.ts`): tối đa 4 request đang chạy mỗi user và 32 cả process (`PROXY_CONCURRENCY`, đếm trong bộ nhớ vì API chạy một process), vượt thì 429 `PROXY_BUSY` (`details: { scope: "user" | "server", max }`, message theo `locale` của user) trước khi tính rate limit và hạn mức tháng. Khi trình duyệt hay agent bỏ đi (`ctx.signal` của operation: response HTTP đóng trước khi gửi xong, hoặc signal của request MCP), request ra đích bị huỷ và slot được trả.
- **Hạn mức** (`proxy-quota.ts`): bắt buộc đăng nhập; rate limit theo user `proxyRateLimit` (120/phút, `rate_limit_windows`) → 429 `RATE_LIMITED`; rồi `limitsFor(plan hiệu lực).proxyRequestsPerMonth` (Free 5 000, Pro `null`) tăng nguyên tử `usage_counters.proxyRequests` của user, vượt thì trả lại lượt vừa tăng và 429 `MONTHLY_QUOTA_EXCEEDED` (`details: { limit: "proxyRequests", max, used }`). Mọi request đã qua rate limit đều được tính, kể cả đích bị chặn hay timeout.
- **Log:** một dòng `proxy` mỗi request: `sub`, host đích (host mock thành `[secret].{MOCK_BASE_DOMAIN}`), method, status hoặc mã lỗi, ms. Không log header, body, path hay query. Logger gắn bằng `configureProxyLogger` lúc khởi động.
- **nginx:** `location ^~ /api/v1/client/` (draft, history, settings) có `client_max_body_size 2m` vì draft nhận tới 1 MiB + 64 KiB (`DRAFT_BODY_LIMIT`), phần còn lại của site giữ 128k. `location = /api/v1/proxy` riêng (`client_max_body_size 16m` ≥ envelope 15 MiB, `proxy_read_timeout 130s`, `proxy_buffering off`, zone `localman_proxy` 5 r/s theo IP). CSP của web: `connect-src 'self' https: http:` (gửi thẳng tới mọi API), `script-src` thêm `'wasm-unsafe-eval'` (QuickJS trong worker), bỏ `upgrade-insecure-requests` (nó đổi request `http://` của user thành `https://`), `img-src` có `blob:` cho preview ảnh của response (preview HTML là iframe `srcdoc` với `sandbox=""`, không cần `frame-src`).
- **Ứng dụng khác trên server .65:** proxy đi ra từ IP của server, kể cả khi vòng qua Cloudflare (sau real-IP, địa chỉ vẫn là `103.72.98.65`), nên luật `allow <IP server>` không phân biệt được proxy với chính server. Location hay app nào tin IP của server phải từ chối request có header `X-Localman-Proxy`; Localman làm vậy ở `location /internal/` (`if ($http_x_localman_proxy) { return 403; }`, `return` là directive an toàn trong `if`).

## Dữ liệu API client theo user

- `client_history`: TTL 90 ngày, tối đa 500 mục mỗi user. Lưu bản nháp còn nguyên `{{var}}` và tóm tắt response (status, ms, size, đường đi); không lưu header hay body response, `finalUrl` chỉ giữ origin và path, nên server không thấy giá trị secret đã nội suy.
- `client_drafts`: tối đa 50 tab mỗi user, mỗi tab tối đa 1 MiB, unique `userSub + tabId`.
- `client_settings`: một bản ghi mỗi user (host cần proxy, ánh xạ `localhost:port` sang URL tunnel, đường đi mặc định, `sendClientIp`). URL tunnel chỉ nhận `https://<label>.<domain>` với `domain` thuộc `TUNNEL_DOMAINS`, không port, path, query hay userinfo (400 `VALIDATION_ERROR`, message theo `locale` của user); `GET /client/settings` trả `tunnelDomains` để web kiểm cùng danh sách. Các thao tác ghi đổi nơi gửi credential (`updateClientSettings`, tunnel mapping, secret-proxy-hosts) không có tool MCP, chỉ đổi từ giao diện.
- **Tunnel theo tài khoản Tunelo** (`modules/tunelo/`, cổng `TUNELO_ACCOUNTS_ENABLED`, cờ web `tuneloAccounts`): `client.listLocalTunnels` (`GET /client/local-tunnels?port=&refresh=`) gộp tunnel của tài khoản (phiên đổi lấy token `tunnels:read` qua `TunnelTokenExchange`) với tunnel của từng máy ẩn danh đã liên kết (link token), gọi song song `GET /api/tunnels` của Tunelo theo tenant (`tunnelResource()`, ghi đè bằng `TUNELO_API_URL` cho dev/E2E, production bắt buộc https, timeout 5 giây mỗi lời gọi). Nguồn lỗi được báo trong `failures` (`unauthorized`/`unavailable`), nguồn khác vẫn trả. Danh sách gộp cache 10 giây theo user và tenant, các lượt đọc cùng lúc dùng chung một lần gọi (`refresh=true` khi "Kiểm tra lại" luôn đọc lại; danh sách mới hơn 2 giây thì chờ đủ 2 giây rồi mới đọc, để bấm liên tục không gọi Tunelo dồn dập mà mỗi lần bấm vẫn có kết quả mới; liên kết hay thu hồi máy xoá cache). Link token bị Tunelo từ chối (401/403, máy đã thu hồi) đánh dấu `deadAt`: không gọi Tunelo bằng nó nữa, Settings hiện máy là "đã thu hồi trên máy" để user xoá. Dòng HTTP chỉ được nhận khi URL là `https://<label>.<domain>` trơn với `domain` thuộc `TUNNEL_DOMAINS` (cùng luật với ánh xạ dán tay), dòng khác bị bỏ. Cần phiên trình duyệt.
- `tunelo_links` (theo tenant): một dòng mỗi lượt `tunelo link` của user, tối đa 20, trong đó tối đa 3 pairing chờ cùng lúc, và mỗi user mở tối đa 5 pairing mỗi 10 phút kể cả pairing đã huỷ (`takeOperationSlot("tuneloLink")`) (429 `RATE_LIMITED`; Tunelo giới hạn pairing theo IP, mà mọi pairing đều từ IP của server Localman, nên 429 của Tunelo cũng trả 429). `pending` giữ `requestId` của `POST /api/links/init` và hết theo TTL (`pendingUntil`, 10 phút như mã của Tunelo); poll (`client.pollTunnelLink`, chỉ dòng của chính user) nhận link token đúng một lần rồi chuyển `linked`, token niêm phong AES-256-GCM bằng `TokenCipher` với keyring `SESSION_ENCRYPTION_KEY`, associated data `tunelo-link:<sub>:<id dòng>`. Tên máy học từ danh sách tunnel. `client.deleteTunnelLink` gọi `DELETE /api/links/self` (lỗi mạng không giữ dòng) rồi xoá; cũng huỷ pairing đang chờ, chỉ xoá dòng còn `pending`: pairing vừa được một lượt poll khác chuyển `linked` thì đi đường thu hồi. Token và `requestId` không bao giờ trả cho trình duyệt hay ghi log. Dòng không đi theo khi chuyển tenant sang bản cài riêng (`COLLECTIONS_NOT_MOVED`: bản cài không mở được keyring phiên).
- **Web** (`features/api-client/tunelo/`, `routing/auto-tunnel-hop.ts`): ánh xạ dán tay đang bật luôn thắng. Không có ánh xạ thì Auto vẫn gửi thẳng trước; bị chặn (hoặc Proxy) thì hỏi danh sách theo port: một tunnel HTTP thì viết lại origin và gửi qua proxy (request có secret luôn hỏi trước, kể cả khi tab chọn Proxy: chọn Proxy không phải là đồng ý với tunnel do router tự tìm; ánh xạ dán tay giữ hành vi cũ) (badge "Qua Tunelo · <máy>" ở ô URL và vùng response), nhiều tunnel thì `choose-tunnel-modal` và nhớ lựa chọn theo địa chỉ local trong `localStorage`, tunnel có Basic Auth thì ghi chú `Authorization` đã dùng cho nó, chỉ TCP thì panel báo và gợi ý `tunelo http <port>`, không có thì panel Tunelo (nút "Kiểm tra lại" đọc lại danh sách, bỏ cache). Tunnel trả 502/404 mà không còn trong danh sách thì panel báo "Tunnel đã dừng"; 404 của chính app (tunnel vẫn còn) được hiện bình thường. POST/PATCH bị chặn khi gửi thẳng không tự gửi lại qua tunnel. Settings > Tunelo có "Liên kết máy" (`tunelo-connect-modal`: mã, lệnh `tunelo link <mã>`, poll 2 giây tới khi xong hoặc hết hạn, lỗi tạm (mạng, 429, 5xx) thử lại 3 lần có giãn cách, 404 coi là hết hạn, đóng thì huỷ) và danh sách máy đã liên kết có nút thu hồi.
- Không gắn project nên không bị xoá theo tombstone của project.

## Localman MCP

`/mcp` trên dashboard (`apps/api/src/modules/mcp/localman-mcp-server.ts`): MCP Streamable HTTP cho AI coding agent (protocol 2026-07-28, client 2025 đi đường legacy stateless của SDK), là OAuth 2.1 resource server của IdP dùng chung. Tool là các operation của registry (xem [operation-registry.md](operation-registry.md)), chạy dưới quyền user của token qua đúng các bước kiểm như REST (`project-access`, `plan-limits`, rate limit thao tác nặng).

- **Discovery:** `GET /.well-known/oauth-protected-resource` và `/.well-known/oauth-protected-resource/mcp` (RFC 9728, `mcp-resource-metadata.ts`) trả `resource` = `{PUBLIC_URL}/mcp`, `authorization_servers` = `[OIDC_ISSUER]`, `scopes_supported` (scope `<toolset>:read|write` của tool với tới được, hiện `mock:read mock:write`; `credentials:write` cố ý không quảng bá, chỉ xin thêm khi gọi tool tạo credential), `bearer_methods_supported: ["header"]`. Client tự đăng ký (DCR) ở IdP và xin token với `resource={PUBLIC_URL}/mcp`. SDK MCP tự thêm `offline_access` khi IdP quảng bá scope này; IdP bỏ qua nó (lúc đăng ký và lúc authorize) mà vẫn cấp refresh token, từ chối scope ngoài resource MCP, và chỉ cấp `credentials:write` cho client khai rõ khi đăng ký. Fake IdP của test/E2E (`auth/testing/fake-idp-dcr.ts`) làm y hệt, kèm test.
- **Xác minh token** (`mcp-access-token.ts`): JWT ES256 `typ: at+jwt` qua JWKS của IdP (`OidcClient`, `jose` tự cache), `iss` của IdP, `aud` chứa `{PUBLIC_URL}/mcp`, `exp` (dung sai 30 giây), có `sub` và `client_id`. Thiếu token: 401 `WWW-Authenticate: Bearer resource_metadata="…"`; token sai: 401 thêm `error="invalid_token"`; token không có scope nào mở được toolset: 403 `insufficient_scope`; tool cần scope token chưa có (ví dụ `mock:write`): 403 `insufficient_scope` của SDK với đúng scope cần. IdP hay JWKS không tới được, hoặc JWKS không hợp lệ (`JWKSInvalid`): 503 `AUTH_UNAVAILABLE`. JWT không thu hồi được: thu hồi grant ở IdP chặn refresh, access token còn dùng được tới `exp` (tối đa 15 phút).
- **Chỉ Bearer:** router đứng trước CSRF guard và parser JSON (tự đọc body, tối đa 4 MB), không bao giờ đọc cookie phiên. Request trình duyệt có `Origin` khác `PUBLIC_URL`/`WEB_ORIGIN` bị 403 `ORIGIN_REJECTED`. Response `Cache-Control: no-store`; kết quả `tools/list` mang `cacheScope: private` (mặc định của SDK).
- **User:** `caller.auth` là `sub` của token (scope nội bộ `user`). Access token không mang hồ sơ, nên `sub` chưa có bản sao thì được tạo tối thiểu (`ensureUserForSubject`: `username` = `sub`, chưa xác minh, không đụng bản ghi đã có); lần đăng nhập web sau đồng bộ hồ sơ từ userinfo. `sub` đã đảm bảo được nhớ trong bộ nhớ 10 phút (tối đa 10.000, `localman-mcp-limits.ts`), nên request sau không upsert lại.
- **Toolset:** chỉ `mock`, `mock-advanced`, `traffic` và `client` (scope IdP cấp cho resource MCP) với tới được, và chỉ khi token có `<toolset>:*`; `mock-advanced` và `traffic` không có scope riêng mà dùng `mock:read`/`mock:write` (`scopeAreaOf` trong `packages/operations/src/types.ts`; đọc log, inbox, callback là `mock:read`, ghi là `mock:write`), không bật mặc định (`?toolsets=mock,traffic` hoặc `enable_toolset`). Operation đổi nơi dữ liệu đi ra ngoài (`setProjectUpstream`, `setWebhookInboxForward`, `setResourceCallbacks`, `testResourceCallback`) và `setRedactHeaders` (gỡ che header rồi đọc qua log) vẫn không có tool; `collab` (thành viên, lời mời, magic link), `users`, `notifications`, `admin` không bao giờ đăng ký trên endpoint này. `?toolsets=` và `enable_toolset` như nền MCP, lựa chọn nhớ theo `sub` + `client_id`; `notifications/tools/list_changed` chỉ tới stream `subscriptions/listen` của đúng `sub` + `client_id` đó (`principal-event-bus.ts`), không phát cho user khác.
- **Scope `mock:read` thấy secret:** tool đọc project trả `secret`, nên token chỉ có `mock:read` cũng đọc được URL mock và URL Hosted Mock MCP (`get_mock_urls`), tức gọi được REST và MCP của mock không bật token. Câu consent của `mock:read` ở IdP cần nói rõ điều này (đã ghi chú gửi IdP, chưa sửa phía IdP).
- **Giới hạn:** mỗi `sub` tối đa `localmanMcpRateLimit` request (mặc định 120/phút, cửa sổ trong Mongo `rate_limit_windows`, `runtime-settings.ts`), vượt thì 429 `RATE_LIMITED` kèm `Retry-After`; tối đa 5 stream `subscriptions/listen` mở cùng lúc mỗi `sub` (stream thứ 6 nhận lỗi JSON-RPC `-32603` trong HTTP 200, như giới hạn của SDK); body là mảng (JSON-RPC batch) bị 400 `-32600`. nginx giới hạn thêm theo IP (`limit_req zone=localman_mcp`, 10 r/s, burst 40). Khi shutdown đóng handler giữa lúc request đang xác thực, request đó nhận 503 `SHUTTING_DOWN`.
- **Link UI:** view project có `uiUrl` (`{PUBLIC_URL}/projects/{id}`); `create_resource_from_schema`, `import_resources` và `get_mock_urls` cũng trả `uiUrl`.

## Form quan tâm gói Pro

Module `apps/api/src/modules/feedback/` (collection `feedback`, field `type`: `pro_interest` và `contact`, xem mục Form góp ý / liên hệ). Web không còn form quan tâm Pro ([ADR-0002](decisions/0002-no-commercial-ui-automatic-pro-period.md)); endpoint và trang admin xem lịch sử vẫn giữ. Không có mail server: form chỉ lưu email để owner liên hệ sau.

- `POST /api/v1/feedback/pro-interest` công khai; có phiên thì gắn `userSub`. Thứ tự kiểm:
  - Rate limit: theo IP (IPv6 gộp theo /64, IPv4-mapped tính như IPv4) 5 lần mỗi 10 phút; người đã đăng nhập còn bị giới hạn theo tài khoản 3 lần mỗi 10 phút (cả hai phải qua). Đếm trong Mongo `rate_limit_windows` theo hash của khoá, tự hết hạn theo cửa sổ (`apps/api/src/lib/rate-limit-windows.ts`, dùng chung với giới hạn lời mời).
  - Honeypot `website`: có giá trị thì trả 201 như thật nhưng không lưu, không báo.
  - Cloudflare Turnstile cho khách khi `TURNSTILE_*` được cấu hình (production bắt buộc). Token phải được giải trên đúng host của `PUBLIC_URL` (bỏ qua với secret thử nghiệm của Cloudflare) và đúng action `pro_interest` của form (token không có action bị từ chối, trừ secret thử nghiệm). Siteverify quá 5 giây hoặc lỗi 5xx thì 503 `TURNSTILE_UNAVAILABLE` (chặn chứ không cho qua); token thiếu hoặc sai thì 400 `TURNSTILE_FAILED`. Bắt buộc `consent: true`.
- `source` thuộc danh sách cố định `PRO_INTEREST_SOURCES` trong `packages/shared`; giá trị lạ được lưu thành `other`.
- Gộp theo email đã chuẩn hoá (unique index một phần trên `type: "pro_interest"`). Mọi lượt gửi được thêm vào `submissions[]` (giữ 20 lượt gần nhất, có cờ `applied`). Câu trả lời của bản ghi chỉ đổi khi cùng danh tính: bản ghi đã gắn tài khoản thì chỉ chính tài khoản đó sửa được (`userSub` không bao giờ bị thay); bản ghi chưa gắn thì khách khác ghi đè được (không phân biệt được khách), còn user đăng nhập chỉ nhận bản ghi đó khi email trùng email đã xác minh ở IdP. `emailMatchesAccount` ghi lại điều kiện xác minh này.
- Sau khi lưu, bot Telegram của Localman báo nền về `OWNER_TELEGRAM_CHAT_ID` (mới, cập nhật hay chỉ lưu lịch sử; nhu cầu, quy mô, nguồn, email che dạng `ng***@gm***.com`; không có tên, ghi chú hay email đầy đủ). Tối đa 10 tin mỗi giờ; tin vượt được đếm và cộng thành "và X lượt khác" (theo ngôn ngữ của owner, xem mục Thông báo) vào tin đầu tiên của cửa sổ kế tiếp.
- Admin (`admin.*`, `guard: ownerOnly` theo `OWNER_SUBS`, `GET /users/me` có `isOwner`): thống kê, danh sách lọc theo nguồn, nhu cầu, đã liên hệ, đoạn email, phân trang (item có `emailMatchesAccount` và `submissions`); xuất CSV trả JSON `{ filename, csv }` (registry chỉ trả JSON, và agent MCP cũng đọc được), UTF-8 có BOM, ô bắt đầu bằng `= + - @`, tab hoặc CR được thêm `'` để chống formula injection; đánh dấu đã liên hệ; xoá theo yêu cầu (`dryRun`).

## Form góp ý / liên hệ

Mỗi form khai `action` Turnstile riêng (`TURNSTILE_ACTIONS` trong `packages/shared/src/feedback-constants.ts`: `pro_interest`, `contact`); API từ chối token giải cho form khác hoặc không có action. Loại, khu vực, trạng thái và giới hạn độ dài cũng nằm ở file này, web và API dùng chung.
- Sau khi lưu, owner nhận tin Telegram (kind `feedback.contact`, throttle riêng như form Pro): loại, trích nội dung tối đa 300 ký tự trên một dòng (bỏ ký tự điều khiển, zero-width, bidi và U+061C; phá link: `https://` thành `hxxps://`, dấu chấm trong tên miền thành `[.]`, chèn word joiner sau `@`, `#` và `/` đầu lệnh bot để Telegram không tạo link hay mention), liên hệ đã che, đăng nhập hay khách, nguồn; không có tên. Tin gửi dạng văn bản thường, không `parse_mode`.
- Admin (`guard: ownerOnly`, có MCP tool): `admin.listContactMessages` (`GET /admin/contact-messages`, mới nhất trước, lọc `status` và `category`, phân trang tới trang 10.000), `admin.updateContactMessageStatus` (`PUT /admin/contact-messages/:messageId/status`, `new` → `read` → `resolved`; lùi về `new` xoá `readAt` và `resolvedAt`) và `admin.deleteContactMessage` (`DELETE /admin/contact-messages/:messageId`, `dryRun`, xoá hẳn nội dung, tên và địa chỉ liên hệ; dùng cho spam hoặc khi người gửi yêu cầu). Không có TTL: tin ở lại tới khi owner xoá. Trang web `/admin/feedback` ("Hộp thư góp ý"), nút xoá có xác nhận và chạy dry run trước.

## Cấu hình sản phẩm

Ngoài biến nền tảng, `apps/api/src/config/feature-env.ts` đọc `MOCK_BASE_DOMAIN`, `MOCK_RATE_LIMIT_PER_SECRET`, `MOCK_RATE_LIMIT_PER_IP`, `MOCK_WRITE_RATE_LIMIT_PER_SECRET`, `MOCK_RESPONSE_BYTES_PER_SECOND` (truyền thẳng cho mock app), `OWNER_SUBS`, `OWNER_TELEGRAM_CHAT_ID`, `TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET_KEY`, `TURNSTILE_VERIFY_URL` và `PUBLIC_SHARING_ENABLED` (cổng của [chia sẻ công khai](#chia-sẻ-công-khai), đọc thẳng trong `main.ts`) (xem `.env.example`). Operation được khai báo tĩnh nên đọc các giá trị này qua `config/runtime-settings.ts`, do `main.ts` cài khi khởi động.

## Dữ liệu

MongoDB 7 chạy dạng single-node replica set (`rs0`), vì dữ liệu resource được thay trong transaction.

Mọi collection thuộc một tenant (`tenantId`, `docs/decisions/0003-tenant-scoped-data.md`): plugin `tenancy/tenant-scope-plugin.ts` lọc và đóng dấu theo tenant trong ngữ cảnh (`tenancy/tenant-context.ts`), mọi index trừ TTL đứng đầu bằng `tenantId`. Bộ đếm, log request và job nền giữ tenant của từng mục và ghi trong tenant đó. Tenant của request đến từ Host (`tenancy/idp-tenant-directory.ts`): host của hoandat.com từ env, domain khác hỏi API nội bộ của IdP (cache, dùng bản cũ khi IdP lỗi); cấu hình khác nhau giữa tenant đọc qua `tenantSettings()`. File `docker-compose.yml` dựng sẵn và tự `rs.initiate` ở lần chạy đầu. Test dùng `MongoMemoryReplSet` một node (wiredTiger) chung cho cả lượt chạy, mỗi file test một database.
